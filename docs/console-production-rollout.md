# Rolling out console login in production

English | [日本語](console-production-rollout_ja.md)

This page is for the operator of a downstream repository ([Upstream and downstream](../README.md#upstream-and-downstream)). It gives the order in which console login goes into production, the checks of each step with their expected results, and the checklist to finish before an Administrator role exists in a production account. How to carry out each operation is in the README; this page links to it and adds what to check and when to stop.

Console login issues Viewer and Administrator from one Worker, one issuer, one signing key, and one OIDC provider per boundary. Read and accept [the accepted limits](../README.md#before-using-console-login-accepted-limits) before step 2: anyone who can deploy the console Worker, or who can touch its secrets or dependencies, holds full control of every account where Administrator is deployed.

**The steps are bound by order, not by time.** Do not start a step until every check of the previous step has its expected result and the result is recorded.

## How to use this checklist

- Record the result of every check: the time, who ran it, and the output. For every deploy, also record the version ID of the deployed Worker. The console tools redact account IDs and emails; raw `aws` output is not redacted (for example `describe-organization` shows the management account's ID and email), so redact it yourself before you put it in a record that others read. Keep the records in a private place of the downstream repository, never in the upstream. The decision in step 5 is made from them.
- **Stop rule (every step):** when a check does not give its expected result, set the var `LOGIN_DISABLED` to `true` on the console Worker and deploy, confirm that issuing returns `503 login_disabled`, then investigate. When only the Admin tier is concerned (from step 4 on), `ADMIN_LOGIN_DISABLED` set to `true` stops only the Admin-tier teams; confirm that their issuing returns `503 login_disabled` while Viewer still works. Do not go on to the next check. Continue only after the cause is fixed and the check passes when run again. In steps 0 and 1 no Worker exists yet: a check that fails there simply stops the rollout until it is settled. This is the same handling as for reconciliation errors in [Reconciling console logins](../README.md#reconciling-console-logins-issue-records-x-cloudtrail); the stop methods are in [Stopping issuance](../README.md#stopping-issuance-console-login).
- **When the Worker cannot stop it:** if you cannot deploy the Worker, cannot confirm `503 login_disabled`, or cannot trust the Worker (its code, secrets, deploy permission, or dependencies may be compromised), do not keep trying the stop switches. Switch to the AWS side: a Deny in the trust policy, deleting the Administrator stack, or deleting the provider (it stops Viewer too); add revoke (L3) for sessions already issued ([Stopping issuance without relying on Cloudflare](../README.md#stopping-issuance-without-relying-on-cloudflare-l2-and-trust-policy-deny)).
- **Checks that cannot be waived:** the cross-tier refusals in the Worker and in AWS (step 4), the checks right after creating the Administrator role (step 5), 0 errors from `mise run console:inspect` and `mise run console:access:inspect`, and the stop switch checks (`LOGIN_DISABLED` and `ADMIN_LOGIN_DISABLED` giving `503 login_disabled`). None of them moves on without a passing re-run, even with a decision of your technical decision maker. A decision can carry over only a measurement that this page marks as not verified (for example the guard statement when the probe provider cannot be made), and the record then holds the reason, the alternative evidence, and a deadline.
- `LOGIN_DISABLED` and `ADMIN_LOGIN_DISABLED` stop new issuance only. Sessions already issued and `aws login` keep working; add revoke (L3) when those must stop too.
- **The person who deploys the console Worker and runs every key operation is someone allowed to issue Administrator, from the first deployment on** ([acceptance b](../README.md#before-using-console-login-accepted-limits)), even while only Viewer is configured. They run `console:key:put`, `console:secrets`, and `console:key:retire` on their own machine, and deploy from it. Do not hand these to an agent, CI, or someone else's terminal.
- What the upstream measured holds for the mechanism (how the Worker, the keys, and the stops behave). Everything tied to your environment (account, zone, tokens, hosts, the deployed Worker) is checked again here. Some protections of the single-Worker shape are measured for the first time in step 4 of this rollout, so **production is where they are measured**: the person who approves the rollout accepts this before step 4. Statements on this page marked "not verified" or "inferred" have not been measured in this shape.

## Step 0: Bring in the latest upstream

- [ ] Pull the upstream and record the upstream commit you pulled, the downstream `HEAD`, and that the working tree is clean (`git status --porcelain` prints nothing). Every later result refers to these, together with the version ID of the deployed Worker. If you pull again during the rollout, record the new commits, run the checks of the current step again, and also run again the checks of earlier steps that the changed parts affect.
- [ ] The commit has what the checks below rely on: the default deploy route `versions upload` + `versions deploy` ([How the Worker is deployed](../README.md#how-the-worker-is-deployed-default-route-and-explicit-route)); one console Worker (`wrangler.console.jsonc`) with the key tasks `console:key:put` / `console:key:check` / `console:key:retire` and the vars `ADMIN_LOGIN_DISABLED` and `ADMIN_ACCESS_MAX_AGE_SECONDS` ([Console login signing keys](../README.md#console-login-signing-keys)); the ledger of retired team names with `--ledger-init` and `--ledger-baseline` ([Ledger of retired team names](../README.md#ledger-of-retired-team-names)); a reconciliation that reports `assume_time_gap`, `identity_mismatch`, `identity_not_compared_admin`, `tier_mismatch`, and `team_tier_mismatch` as errors and prints the lines `excluded assumes (not console)` and `admin issues`; and the task `console:exposure-check` ([Checking the console issuers from outside](../README.md#checking-the-console-issuers-from-outside-daily)). If one is missing, do not go on with that version.
- [ ] Your console wrangler config (`wrangler.<name>-console.jsonc`) sets `workers_dev` and `preview_urls` to `false` and serves the two hosts (the portal and the issuer) with Custom Domains ([Hosts](../README.md#hosts)).

```bash
git pull --no-rebase upstream main
git rev-parse upstream/main          # record this commit (upstream)
git rev-parse HEAD                   # record this commit (downstream)
git status --porcelain               # nothing: the working tree is clean
mise tasks | grep console:           # console:key:check, console:reconcile and console:exposure-check are listed
```

## Step 1: Check the target account

Run these in each account that will get console login, with a read-only profile for a principal other than the console roles.

- [ ] **Not the management account of an Organization.** Expected: the `MasterAccountId` of `aws organizations describe-organization` differs from the `Account` of `aws sts get-caller-identity` (or the account is not in an Organization). If `describe-organization` is refused for lack of permission, confirm it another way (for example ask the administrator of the Organization) and record how you confirmed it. If it is the management account, stop: do not set up console login there, and escalate to your technical decision maker.
- [ ] **No role with a console role name.** Expected: `aws iam get-role` returns `NoSuchEntity` for every role name in your config (for example `FederatedAwsBridgeViewer` and `FederatedAwsBridgeAdministrator`), and no role is under the path `/awsbridge-console/`. If one exists, stop and find out who made it; do not adopt or overwrite it.
- [ ] **No console OIDC provider yet.** `aws iam list-open-id-connect-providers` lists no provider for your console issuer host. Save the output as the baseline (it contains the account ID: keep it in `.secrets/`, never in a public repository).
- [ ] **The MCP relay is left alone.** Write down the status of the MCP stack (`AWSBRIDGE_STACK_NAME`) and the ARN of the MCP provider. The console stacks have other names (`awsbridge-console-base`, `awsbridge-console-kind-<kind>`, and separate names for the Admin-tier stacks) and never update the MCP stack or its provider. After each later step, confirm both are unchanged.
- [ ] **Leftover check.** `mise run poc:g2:clean-check` is a read-only tool written for the upstream's trial environment. Expected: exit code 0 and no `NG` line. Its limits: it recognizes provider hosts only by fixed prefixes (the README's `awsbridge-console.` and `awsbridge-oidc-console.`, plus `awsbridge-admin-console.` and `awsbridge-oidc-admin-console.` from the earlier per-tier hosts), so with other host names compare against the baseline by eye; it checks only the stacks you name with `--stack`; and its Cloudflare part is `SKIP` without its read token, still with exit code 0.

```bash
aws sts get-caller-identity --profile <read-only profile>
aws organizations describe-organization --profile <read-only profile>
aws iam get-role --role-name FederatedAwsBridgeViewer --profile <read-only profile>          # NoSuchEntity
aws iam get-role --role-name FederatedAwsBridgeAdministrator --profile <read-only profile>   # NoSuchEntity
aws iam list-roles --path-prefix /awsbridge-console/ --profile <read-only profile>            # no roles
aws iam list-open-id-connect-providers --profile <read-only profile> > .secrets/providers-before.json
mise run poc:g2:clean-check -- --profile <read-only profile> --baseline .secrets/providers-before.json \
  --stack awsbridge-console-kind-default
```

## Step 2: The console Worker and Viewer only

Set up the console Worker with the Standard tier and the Viewer role, following steps 1 to 7 of [Order of the first setup (console login)](../README.md#order-of-the-first-setup-console-login). In this step the config has no Admin-tier team and no Admin-tier role. Deploy the Worker with `LOGIN_DISABLED` set to `"true"` and keep it there until the checks below pass.

- The first generation has no ledger to compare with: run `mise run console:config:generate -- --ledger-init` and record that you did (it is printed and kept as `ledgerInit` in the meta of `stacksets.json`). Keep the generated `stacksets.json` in a private place as the baseline for `--ledger-baseline` in a new checkout.
- [ ] Before the first deployment, `mise run console:inspect -- --profile=<p>` in each target account (required after `--ledger-init`): the only errors are `role_missing` and `provider_missing` (nothing is deployed yet). A `trust_team_retired`, `trust_team_tier`, or `unlisted_role` means a console role is already there: stop and find out where it comes from.
- The first deployment, and any change of a Custom Domain, takes the explicit route with a short-lived token of your own that has the zone permissions; discard it afterwards ([How the Worker is deployed](../README.md#how-the-worker-is-deployed-default-route-and-explicit-route)). Before you discard it, check once with it that no Route hits the two console hosts, as in [Checking the console issuers from outside](../README.md#checking-the-console-issuers-from-outside-daily) (all pages, wildcards included; a list that cannot be read is not 0 Routes).
- Daily deploys use a token that is "Individual Workers Editor for the console Worker only, no zone permissions", held by the person described above.

### Before the first issuance

With `LOGIN_DISABLED` still `"true"`:

- [ ] `mise run console:key:check`: no `[NG]` (the binding is a `secret_key`, the discovery and JWKS match the vars, the key cannot be extracted, `exportKey` fails, the self-verification passes). If the binding is not a `secret_key` or `exportKey` succeeds, stop and escalate to your technical decision maker.
- [ ] `mise run console:access:inspect`: 0 errors (Cookie Path enabled on the entry application and on every team application; [Access applications](../README.md#access-applications-for-console-login-cookie-path)).
- [ ] **workers.dev and Preview URLs do not answer.** Neither the Worker's workers.dev URL nor a Preview URL returns a response of the Worker (no portal page, no JSON, no issuer document); a 404 or a Cloudflare error page is expected. These would be entrances that skip Access: if one answers, fix `workers_dev` / `preview_urls`, deploy on the explicit route, and check again.
- [ ] **The daily token is limited to the console Worker.** With that token, try once to add a Worker Route for each of the two console hosts (the portal and the issuer), for example with a `POST` to the zone's Workers Routes API (`/zones/{zone_id}/workers/routes`). Expected: 403 every time. If any attempt succeeds, delete what it created at once, treat the token's scope as wrong (revoke it and make a new one), and check again.
- [ ] **The default route keeps the settings.** Deploy once on the default route without changing anything that matters (for example only a deploy message), and compare before and after: vars, the `secret_key` bindings, Custom Domains, the Workers Logs (observability) settings, `workers_dev` and `preview_urls` (both still `false`), and `LOGIN_DISABLED` are all unchanged. Then run `mise run console:key:check` again: no `[NG]`. That the key survives the default route was measured before only on the earlier per-tier Admin Worker; for the single console Worker it is inferred, and this is the first check of it.
- [ ] `AWSBRIDGE_CONSOLE_LOGS_WORKERS` holds the name of the console Worker as your downstream wrangler config names it (the default is the upstream name `awsbridge-console`, which may not be yours). The first `console:reconcile` with `--logs-api` below must read the records successfully (`source: api`, not exit code 2).
- [ ] `mise run console:exposure-check`: exit code 0 and `[OK]` for every boundary.
- [ ] After the base stack and the role stacks: `mise run console:inspect -- --profile=<p>` reports 0 errors, and the MCP stack and provider are unchanged.

### On the day of the first issuance

Set `LOGIN_DISABLED` to `"false"`, deploy, and record the time (T0). Issue for the Viewer from the portal (and with `aws login` if you use it), and record how many issuances you made. Wait until CloudTrail has the events. Allow about 30 minutes as a guide (not measured); the tool leaves records newer than its propagation lag (default 300 s, `--lag-seconds`) as `pending`, so if they are not settled yet, wait longer and run again. Then on the same day:

- [ ] **workers.dev and Preview URLs still do not answer** after the deploy that set `LOGIN_DISABLED` to `"false"` (the same check as before the first issuance).

- [ ] Record the CloudTrail delay: the time of the issuance, and, by running `console:reconcile` again, the time the assumption first appeared in CloudTrail (material for choosing the overlap `--overlap-seconds` in the decision of step 5).
- [ ] `console:reconcile` (command below): exit code 0 and `errors: 0`; `regions: read <n>/<n>` with both numbers equal; `unverifiable: 0, truncated lines: 0, unreadable lines: 0, pending: 0` (with `pending` above 0, `matched` falls short of your issuances); `matched` equal to the console assumes and to the number of your issuances (each `jti` matched one to one); `identity: compared <n>, not compared 0 (admin 0)`; `excluded assumes (not console)` at its expected value (0 when MCP is not used in the account; otherwise only the MCP roles, checked as in the README); `coverage: first run`. Read every warning.
- [ ] **One `aud` per request.** Logging in through the entry and through each team path works (the Worker accepts an Access JWT with exactly one `aud`). A request to `/t/<team>/key-check` sent with a token of the entry application is refused with `403 unknown_audience`, and one sent with a token of another team's application with `403 team_mismatch` (if Access does not refuse it first). Expected: both are refused, and neither returns the key-check's 200 JSON.
- [ ] `mise run console:exposure-check`: exit code 0.

```bash
mise run console:reconcile -- --profile <p> --logs-api --since <T0 minus 5 minutes>
mise run console:exposure-check
```

## Step 3: At least one clean day of daily checks

From the day after the first issuance, run the two daily checks in [Daily operations](../README.md#daily-operations).

- [ ] At least one daily run after the first-issuance day in which `console:reconcile` exits with 0, shows `errors: 0`, and shows `excluded assumes (not console)` at its expected value, and `console:exposure-check` exits with 0.
- On an error, follow the stop rule and the handling in [Reconciling console logins](../README.md#reconciling-console-logins-issue-records-x-cloudtrail). An unexpected excluded count is investigated as described there. The clean day counts only after the cause is settled.
- Run it every day without `--since`. From the second day on, the start comes from the state file (the end of the confirmed interval minus the overlap, 24 hours by default). Check that the `read start:` line of the output says `from the state`. A query covering the older part can be sampled into `record_read_incomplete`, and if you skip more days than the period measured to read without sampling, the current way the tool reads cannot confirm that the interval in between was read completely (that period has not been measured yet). Exit code 0 does not prove that no assumption showed up late outside the overlap.
- When exit code 1 appears, record the findings (time, code, the start of the `jti`, role) outside the tool the day they appear. What the tool guarantees is only that a run with an error in the window it read does not advance the state; a detected error is not kept in the state. Once the error's time leaves the window (about 6 days pass, or `--overlap-seconds` or `--since` changes), the next run does not read it and the state advances with exit code 0 (the `oldest error finding:` line of the output shows when it leaves). Until the cause is known, do not change `--overlap-seconds` or `--since`, and do not rebuild the state file. Resume only after recording the resolution or the acceptance.
- If errors keep the state from advancing and the window grows too old to read, record which interval could not be verified, keep the evidence within the retention, read it again in short windows, and only then let a person decide. The two ways to resume are kept apart: resume after verification, when every short window has been read, and resume by accepting it unverified, when a person accepts the interval that cannot be read. When accepting, before rebuilding the state file, keep a record of the acceptance outside the tool: the account, the interval that could not be verified, the unresolved findings, the reason, who decided and when, and the state file before and after the change. Do not delete the state file silently (the operations in [Reconciling console logins](../README.md#reconciling-console-logins-issue-records-x-cloudtrail)).
- Anyone who can write the state file can move the confirmed interval forward and make the tool skip it. Keep it where only the people who run the reconciliation can write it. For an audit that reads everything again, use `--since 6d`.

## Step 4: The Admin tier with a weaker role, without Administrator

Add one Admin-tier team and one weaker Admin-tier role, and issue for it once, as in [Adding the Admin tier and the Administrator role](../README.md#adding-the-admin-tier-and-the-administrator-role). **Do not create the Administrator role in this step.** The weaker role is a role of the Admin tier (path `/awsbridge-console/admin/`, `MaxSessionDuration` of 1 hour, the Admin guard policy, a trust policy for the Admin-tier team only, as the reference template makes it) whose permissions are `ReadOnlyAccess` (in `managedPolicyArns`) plus only the Allows that the guard-statement probe below needs, limited to the probe provider (a policy document given in `inlinePolicyFiles`).

- Give the Admin-tier team a new name that no Standard team uses and that is not in the ledger, create its Access application with a short session (`admin_session_duration`, default 15 minutes) and Cookie Path, add the team and the weaker role to the config, and regenerate (in a new checkout, pass the kept `stacksets.json` with `--ledger-baseline`).
- Create the weaker role in a **separate stack** whose name does not match `awsbridge-console-kind-<kind>`. Keep its `<Role>Teams` parameter empty in the Viewer stack, keep `AdministratorTeams` empty in every stack, and look at the change set of every update of the Viewer stack.
- The person allowed to issue Administrator deploys the Worker on the default route and runs `mise run console:key:check` again: no `[NG]`. With `--team <team>` (the Admin-tier team) it also opens the key-check on the path of the Admin-tier team.
- Before the first Admin-tier issuance: `mise run console:access:inspect` 0 errors (now including the Admin-tier application), `mise run console:inspect -- --profile=<p>` 0 errors (no `trust_team_tier`, no `trust_team_retired`).
- **Order around `ADMIN_LOGIN_DISABLED`:** (1) deploy the Admin-tier team with `ADMIN_LOGIN_DISABLED` set to `"true"`, run the checks just above, and confirm that a login on the Admin-tier team's path returns `503 login_disabled`; (2) set it to `"false"`, deploy, and record the time and the Worker version ID; (3) run the checks below, recording the time and the number of successful Admin-tier issuances of each; (4) on a failure, set it back to `"true"`, deploy, and confirm `503 login_disabled` before you investigate.

Checks (stop with `ADMIN_LOGIN_DISABLED` on a deviation that concerns only the Admin tier, otherwise with `LOGIN_DISABLED`, and escalate to your technical decision maker):

- [ ] **Cross-tier refusals in the Worker.** With the real Worker and Access: a login for the weaker role sent to a Standard team's path is refused with `404 not_listed`; a request to the Admin-tier team's path with a token of a Standard team's application is refused with `403 team_mismatch` (or by Access first); a request with a token of the entry application is refused with `403 unknown_audience`. Expected: none of them calls STS (no matching assumption in the reconciliation).
- [ ] **Cross-tier refusal in AWS.** Show the list of operations to a person and get approval first. With a principal other than the console roles, change the team value (`aws:RequestTag/awsbridge_team`) in the weaker role's trust policy to a name that is no team (`aws iam update-assume-role-policy`), issue for the weaker role from the Admin-tier team with the real Worker, and expect `sts_denied`. Then restore the trust policy with the API, confirm with `aws iam get-role` that it is back, issue once and expect success, and confirm with drift detection that the stack has no difference. Other cases (a JWT without the team tag, and so on) are not verified in this shape; that they behave as before is inferred from IAM evaluating the trust policy the same way for any issuer.
- [ ] **The guard statement for the single host.** Have a person approve creating and deleting a probe provider. With a principal other than the console roles, create a probe provider under the issuer host (for example `https://<issuer-host>/probe`) that has no key, whose JWKS returns 404, and that no role trusts. From a session of the weaker role, try `TagOpenIDConnectProvider`, `AddClientIDToOpenIDConnectProvider`, and `DeleteOpenIDConnectProvider` on the probe provider, and `CreateOpenIDConnectProvider` on another path of the same host. Expected: each is `AccessDenied` by an explicit Deny naming `AwsbridgeConsoleGuardAdmin`. Never aim these at the real provider (Viewer uses it too). Without the Allows on the weaker role, the result is an implicit deny and proves nothing. Delete the probe provider afterwards. If the probe provider cannot be made, record the guard statement as not verified, with the reason, the alternative evidence, and a deadline; do not count earlier measurements of the per-tier shape as its proof.
- [ ] **One key rotation.** Rotate the boundary's key once as in [Key rotation](../README.md#key-rotation) (new key in the JWKS, sign with it, remove the old kid). Expected: issuing for Viewer and for the weaker role does not break, and `mise run console:key:check` shows no `[NG]` after the old kid is removed. The key is shared, so this affects Viewer.
- [ ] **A person not allowed in the Admin-tier team.** With another identity, the Access application of the Admin-tier team refuses; with that person's token of a Standard team's application, the Worker refuses the Admin-tier path with `403 team_mismatch`. If the Admin-tier application is misconfigured and lets the person through, the Worker cannot refuse (the JWT carries the Admin-tier AUD); the Access policy is the only guard there.
- [ ] **The reconciliation shows the Admin tier.** For a window you choose (`--since`), `mise run console:reconcile` shows `errors: 0`, `admin issues: <n>` where `<n>` equals the number of successful Admin-tier issuances you recorded in that window, each at a recorded time, and `admin 0` in the identity line.
- [ ] **The Admin-tier Access application, checked by a person.** 0 errors from `mise run console:access:inspect` does not cover who the policies allow (include, require, and exclude rules), the session duration, or other applications, Allow policies, or Bypass rules covering the same paths. Read all policies and the session settings of the Admin-tier application and of anything else that covers `/t/<team>` of the Admin-tier team, and record them.
- [ ] **The age limit.** A page or a login on the Admin-tier team's path with an Access JWT older than `ADMIN_ACCESS_MAX_AGE_SECONDS` (default 15 minutes) is refused with 401. Record also whether Access issues a new JWT inside its session without re-authentication, and whether the IdP signs the person in again without a prompt after the Access session ends (not verified; it decides how to read the limit).
- [ ] **`ADMIN_LOGIN_DISABLED`.** Set to `true`: a login on the Admin-tier team's path returns `503 login_disabled` while a Viewer login still succeeds. Set it back.
- [ ] **What the logs keep.** Read one invocation record that the platform writes to Workers Logs. Expected: it does not contain the request header `Cf-Access-Jwt-Assertion`, the request body, or the `Location` of the redirect. If it does, narrow what is logged or count reading the logs in the accepted limits.
- [ ] Record whether the CloudTrail `AssumeRoleWithWebIdentity` event shows the session tags (read only; the reconciliation does not use them).
- [ ] `mise run console:inspect -- --profile=<p>`: 0 errors after all of the above. `mise run console:exposure-check` exits with 0. The daily checks stay clean, `admin issues` shows nothing you did not do, and the MCP stack and provider are unchanged.

## Stopping drill (before step 5)

Do this once before the decision in step 5. Each stop is complete when a request is refused, not after a fixed time ([Stopping issuance](../README.md#stopping-issuance-console-login)).

- [ ] **Viewer.** The stop switch: `LOGIN_DISABLED` set to `true` makes issuing return `503 login_disabled`; then set it back. Stopping one person: `mise run console:stop:apply` with your own SourceIdentity makes requests of your Viewer session fail ([Stopping one person](../README.md#stopping-one-person-for-console-login)). It needs `--stops`, `--reason`, and `--yes` to write, and you run it from another entry point (such as IAM Identity Center), not from a session of a console role. Revoke (L3) on the Viewer role refuses sessions issued before it. Releasing the one-person stop must wait for the release conditions (at least the role's `MaxSessionDuration`), so plan the drill over two days.
- [ ] **Stopping only the Admin tier.** `ADMIN_LOGIN_DISABLED` as in step 4, and a Deny in the weaker role's trust policy ([Denying in the role trust policy](../README.md#denying-in-the-role-trust-policy)): issuing for the weaker role fails with `sts_denied` while Viewer keeps working. Restore it by hand, issue once, and confirm with drift detection. There is no provider deletion that stops only the Admin tier ([Stopping issuance without relying on Cloudflare](../README.md#stopping-issuance-without-relying-on-cloudflare-l2-and-trust-policy-deny)); do not delete the provider in production for the drill.
- [ ] **Administrator inventory.** Run steps 2 to 4 of [Inventory of what an Administrator left behind](../README.md#inventory-of-what-an-administrator-left-behind-console-login) once (providers, CloudTrail, the IAM listing). The Administrator role does not exist yet, so skip its step 1. Keep the listing as the baseline to compare with after an Administrator has been used (it contains account IDs; never put it in a public repository). Also take the current resource policies outside IAM (for example S3, KMS, and Lambda, for the services you use) as their baseline. Check whether `sourceIdentity` appears on the events of operations made in your Viewer session; if it does not, the inventory has to pick events another way, as the README says.

## Step 5: Decide before adding Administrator

**Stop here.** Present the results to your technical decision maker again and get their technical approval. Adding the Administrator role to a production account also needs the approval of a person, made from the records. The technical review of your decision maker does not replace it.

### What the decision needs

- [ ] The results of steps 0 to 4 and of the drill, each with its expected result, how every deviation was settled, and which statements stay not verified.
- [ ] The measured CloudTrail delay: the distribution of the delay recorded for issuances from step 2 on and the period observed, how the overlap `--overlap-seconds` was chosen against it, and how much delay beyond the overlap is accepted. A finite observation cannot guarantee the maximum delay, and exit code 0 of the reconciliation does not prove that no assumption showed up late outside the overlap.
- [ ] The account and its Organization: which Organization the account belongs to, that it is not the management account, who administers the Organization, and which controls (such as SCPs) apply to the account.
- [ ] Where the signing keys are: the Cloudflare account that holds the console Worker and its `secret_key` bindings, who can change the console Worker (code, vars, secrets, dependencies), and who holds tokens that can change the zone of the console hosts (DNS, Routes, Custom Domains). Anyone on these lists can sign an Administrator JWT or replace the issuer, even if they only ever handle Viewer.
- [ ] The accepted limits, read and accepted by the person who approves: [acceptances a to e](../README.md#before-using-console-login-accepted-limits); the issue records are written by the console Worker itself, so against anyone who can write to the console Worker (including people who handle only Viewer) the reconciliation is not independent detection ([Reconciling console logins](../README.md#reconciling-console-logins-issue-records-x-cloudtrail)); watching the zone's configuration is the zone owner's operation, and the comparison from the outside is detection, not prevention ([Checking the console issuers from outside](../README.md#checking-the-console-issuers-from-outside-daily)); the ledger of retired team names guards against mistakes, not against anyone who can write the config.
- [ ] The approval itself, with its date and the commit from step 0.

### After the approval: the Administrator stack

First set `ADMIN_LOGIN_DISABLED` to `"true"`, deploy, and confirm that a login on the Admin-tier team's path returns `503 login_disabled`. Keep it there until every check right after the creation (below) has passed. Then add the Administrator to the config (assigned to the Admin-tier team), regenerate, deploy the Worker, and create the Administrator role as in [Adding the Admin tier and the Administrator role](../README.md#adding-the-admin-tier-and-the-administrator-role):

- [ ] Between the regeneration and the creation of the stack, `mise run console:inspect` reports `role_missing` for the Administrator role; that is the only expected error.
- [ ] A **separate stack** whose name does not match `awsbridge-console-kind-<kind>` (for example `awsbridge-console-admin-default`), with only `AdministratorTeams` set.
- [ ] The creation change set contains **only an `Add` of `AdministratorRole`**. Otherwise, do not execute it.
- [ ] Right after the creation and before the first issuance: `aws iam get-role` shows a trust policy that names the console provider and whose team condition holds only teams of the Admin tier, and `aws iam list-attached-role-policies` shows the Admin guard policy attached. Otherwise, abort (below).
- [ ] `mise run console:inspect -- --profile=<p>` right after the creation: 0 errors (no more `role_missing`, no `trust_team_tier`).
- [ ] In the Viewer stack (for example `awsbridge-console-kind-default`), `AdministratorTeams` stays empty. Before every update of it, look at the change set; if `AdministratorRole` appears, do not execute it.
- [ ] After every check above has passed: set `ADMIN_LOGIN_DISABLED` to `"false"`, deploy, record the time and the Worker version ID, and confirm the first Administrator issuance. On a failure, set it back to `"true"` and deploy.
- [ ] After the first Administrator issuance, on the same day: for the window since that time, `console:reconcile` shows `errors: 0`, `admin issues: <n>` equal to the successful Admin-tier issuances you recorded in the window, and `admin 0` in the identity line; `console:exposure-check` exits with 0.
- [ ] Only after the first Administrator issuance is confirmed, delete the weaker role (its stack, and the role in the config), regenerate, deploy the Worker, and run `mise run console:inspect` again.
- To abort: **delete the Administrator stack, and remove the Administrator from the config and regenerate**, so that the generated files and the portal list do not keep it. Then deploy the Worker and confirm that the portal no longer shows the Administrator.
- To stop Administrator assumptions without Cloudflare: [Denying in the role trust policy](../README.md#denying-in-the-role-trust-policy), or deleting the Administrator stack. Deleting the provider stops Viewer too ([Stopping issuance without relying on Cloudflare](../README.md#stopping-issuance-without-relying-on-cloudflare-l2-and-trust-policy-deny)). While a trust-policy Deny is in place, do not update the stack: whether an update that changes the trust policy removes the Deny has not been measured.
