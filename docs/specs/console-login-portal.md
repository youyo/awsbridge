## 1. 目的と範囲

### 1.1 目的

ログインした人が、自分の入れる「アカウント × ロール」の一覧から選び、次の 2 つのどちらかを行えるようにする。

1. AWS コンソールに入る（フェデレーションのログイン URL を作り、ブラウザを送る）
2. `aws login` で CLI の認証情報を得るための手順を知る（ポータルは手順を表示するだけ）

困りごと（入口の数・新しい Organization の受け入れ・権限の付与管理）のうち、「入口の数」をこの画面で解く。

### 1.2 ポータルの責務

| 責務 | 内容 |
|---|---|
| 一覧の表示 | 通ってきた Access アプリ（= チーム）を受け付ける「アカウント × ロール」を、表示用インベントリから並べる。検索・絞り込み・お気に入り・最近使ったもの |
| ログイン | 選んだロールについて、短命 JWT の署名 → STS → `getSigninToken` → コンソールへの送り出しを行う |
| `aws login` の案内 | 選んだアカウント × ロールに合わせた `~/.aws/config` の断片と手順を表示する |
| エラーの説明 | 拒否・期限切れ・一覧のずれなどを、利用者が次に何をすればよいか分かる形で表示する |
| 発行の記録 | 発行ごとに監査ログを残す（URL と認証情報は残さない） |

### 1.3 やらないこと

| やらないこと | 理由・代わり |
|---|---|
| 権限の編集（誰をどのチームに入れるか、どのチームがどのロールに入れるか） | 権威は Entra のグループ（所属）と、種類の定義 → StackSets → 信頼ポリシー（割り当て）にある。ポータルは読むだけ |
| 「入れるかどうか」の最終判断 | 信頼ポリシーが決める。一覧は目安（§5.5） |
| 利用者の所属チームの一覧化 | M2 では Worker は所属を知らない（§7） |
| CLI の認証情報の直接発行（アクセスキーの表示・ダウンロード、`credential_process`） | 認証情報を Worker の外に出さない。CLI は `aws login` に任せる（利用者の回答: CLI は `aws login` で困っていない） |
| ログイン URL の表示・コピー | URL はセッションそのもの。302（または POST）で渡すだけ（§9.8） |
| JIT の申請・承認 | Entra の PIM に任せる（段階 3 で決める） |
| 管理アカウントへのログイン | 管理アカウントにはコンソールログイン用ロールを置かない。既存の Identity Center か break-glass で入る |
| サーバー側での個人の設定の保存 | 当面はブラウザの localStorage だけ（§12 の未決事項） |

## 3. 画面一覧と画面遷移

### 3.1 URL の形（チームの分け方は未決）

M2 では、チームごとに Access アプリを分ける。分け方は 2 通りあり、N1（1 つのホストでパスごとに Access アプリと AUD が分かれるか）の結果で決める（§12.3）。

| 案 | Standard の URL | Admin の URL | 利点 | 欠点 |
|---|---|---|---|---|
| **R-P パスで分ける**（第一案） | `https://portal.<domain>/t/<team>/` | `https://admin-portal.<domain>/t/<team>/` | ホストと証明書が 1 つで済む。localStorage（お気に入り・最近使ったもの）がチームをまたいで共有される | 同じホストに Access アプリが並ぶ。Access の「Cookie Path」の設定次第で、チームを切り替えるたびに Cookie が上書きされ、再認証のリダイレクトが起きる [確認済み: Cloudflare の文書に Cookie Path の挙動の記載。実際の切り替えの見え方は未検証] |
| R-H ホストで分ける | `https://<team>.portal.<domain>/` | `https://<team>.admin-portal.<domain>/` | Cookie と画面の状態がチームごとに完全に分かれる | ホストと DNS がチームの数だけ要る。チームを足すたびに Worker の Custom Domain（wrangler の設定）も足す。localStorage がチームをまたいで共有されない |

`portal` / `admin-portal` のラベルは例で、実際のホスト名は下流の設定ファイル（`portal.standardOrigin` / `portal.adminOrigin`。§11.3）で決める。

#### ホスト名を自社ドメインにしたことの影響

ポータルのホストは自社ドメイン（`<domain>`。Cloudflare のゾーン）に置く（§0 の利用者の決定）。`workers.dev` は使わない。

| 項目 | 内容 |
|---|---|
| Worker の公開 | Workers の **Custom Domain** で、ホスト全体を Worker に向ける（Worker がオリジンになる。DNS レコードと証明書は Cloudflare が作る）[確認済み: Cloudflare の文書「Custom Domains」]。Route（`<host>/*`）は、別のオリジンの前に置く場合の方式なので使わない。Custom Domain は下流の `wrangler.<name>.jsonc` の `routes`（`custom_domain: true`）に書く |
| R-P と R-H | 自社ドメインなので、どちらも取れる（`workers.dev` では Worker ごとのホストが 1 つに決まるので、R-H は取りにくかった [推測]）。R-P は Custom Domain が Standard・Admin で 1 つずつ。R-H はチームの数だけ要る（Custom Domain はワイルドカードを受け付けない [確認済み: 同じ文書]）。R-H の `<team>.portal.<domain>` は 2 段のサブドメインで、Universal SSL の対象外だが、Custom Domain を作ると、そのホスト用の証明書が別料金なしで発行される [確認済み: 同じ文書の Certificates の節] |
| G-1 への影響 | 証明書は R-H を退ける理由にならなくなった。決め手は N1（パスごとに AUD と Cookie が分かれるか）と、チームを足す手間（R-P は Access アプリだけ、R-H は Access アプリと Custom Domain）。第一案は R-P のまま |
| Access アプリ | Access アプリの対象（ドメインとパス）は、設定ファイルの `portal.*Origin` とチーム名から Terraform で作る（§9.1・§11.4） |
| `Issuer`（フェデレーション） | S5 の URL（`<team-base>/expired`）。設定ファイルの `portal.standardOrigin` から作る（§6.3）。ホスト名を変えると、発行済みのコンソールのセッションが切れたときの戻り先が古いホストになる |
| OIDC の issuer（STS が信頼する URL） | フェデレーションの `Issuer` とは**別物**。各アカウントの IAM OIDC プロバイダーの URL で、StackSets で全アカウントに配る。ホストとパスは N9 で決める（この文書の範囲外）。`workers.dev` に置かない方がよい（Cloudflare のアカウントのサブドメインに縛られ、変えると全アカウントのプロバイダーを作り直すことになる）[推測]。ポータルと同じホストのパス（Bypass の Access アプリ）にするか、別のホスト（例 `idp.<domain>`）にするかは未決（§12.2 の G-8） |
| 変えにくさ | ポータルのホスト名は `Issuer`・ブックマーク・Access アプリ・CSRF の Origin の検査に入る。段階 1 の前に下流の設定で確定する |

この文書では、チームの起点の URL を **`<team-base>`** と書く（R-P なら `https://portal.<domain>/t/<team>`、R-H なら `https://<team>.portal.<domain>`）。どちらの案でも次を守る。

- **チームは検証した Access JWT の AUD だけから決める**。パスやホストのチーム名は経路の振り分けにだけ使い、AUD から決めたチームと食い違えば拒否する（`team_mismatch`）
- 未知の AUD には何も発行しない（`unknown_audience`）

ASCII の図は構成を示すもので、見た目の確定ではない。アカウント ID は `xxxx-xxxx-0001` のように伏せ、利用者は `<email>` と書く。

### 4.1 S0 入口（Standard）

- チームの一覧は Worker の設定（AUD → チームの対応と同じもの。下流の設定ファイルの `teams` のうち、このデプロイの階層のもの。§11）から出す。表示名は `displayName`。所属は分からないので、全チームを並べる
- チームが 1 つだけの設定（個人用など。§11.7）では、S0 はそのチームの S1 へ移すだけにする [推測: 実装の案]
- 最近使ったもの（localStorage）にアカウントの email は入れない（§5.6）
- 「前回入れた」は localStorage の記録（そのチームの S1 を表示できたことがある）。所属の判定に使わない
- 「開く」は `<team-base>/a/<account-id>` へのリンク（GET）。ログインは S2 の POST で行う
- 最近使ったものは R-P なら全チーム分を出せる。R-H ではホストが違うので出せない（§3.1）

### 4.2 S1 一覧（Standard、チーム `dev`）

- 行を選ぶと S2 へ。ロールのボタン（`[Developer]`）は S2 をそのロールを選んだ状態で開く。**一覧から直接ログインはしない**（1 クリックで POST を飛ばさない。誤操作と CSRF の面を減らす）。S2 で 1 回押せばよいので、操作は 2 回で済む
- 検索は名前・ID（ハイフンの有無を問わない）・email・Organization・種類に部分一致。email は大文字と小文字を区別しない。ブラウザ内で絞り込み、JavaScript がないときは `?q=` でサーバー側の絞り込みに切り替わる（§10.1）。`?q=` に email が入ると要求の URL がログに残りうるので、JS なしの検索で email を対象にするかは P-7 の結果で決める（§5.6）
- email は 2 行目に小さく出す（1 行目の列を増やさない）。お気に入り・最近使ったものの欄は localStorage から出すので email を出さない（§5.6）
- 管理外の行の email は、既定では出さず、検索の対象にもしない。出すかどうかは下流の設定（`inventory.accountEmail`。§11.3）で決める
- 「チーム ▼」は全チームへのリンク。選ぶと別のチームの S1 に移る（§7）
- 一覧が空のとき: 「このチームで入れるアカウントは一覧にありません」と、別のチームで同じ検索語を開くリンク（`<他チームの team-base>/?q=<検索語>`）を出す。他のチームの一覧の中身は見せない
- 「管理外」の行は、先方の組織のアカウント。先方の設定が更新されていないと拒否されうる（§5.5）

### 4.3 S2 アカウントの詳細とログイン

```

│ ← 一覧へ   svc-b-prod（xxxx-xxxx-0006）  ★                 チーム: 開発 (dev)   │
├────────────────────────────────────────────────────────────────────────────┤
│ Organization: org-main（管理下）   種類: C                                   │

│                                                                            │

│   (•) Developer  /awsbridge-console/std/FederatedDeveloper セッション: 8 時間 ※1 │

│ リージョン: [ap-northeast-1 ▼]                                               │
│                                                                            │
│ ┌───────────────────────────────┐  ┌───────────────────────────────┐       │
│ │   コンソールを開く（新しいタブ）    │  │   CLI で使う（aws login の手順）  │       │

│                                                                            │
│ ▼ 開いたコンソールが別のアカウント・ロールのままのとき                            │
│   同じブラウザに別のコンソールのセッションが残っていると、切り替わりません。          │
│   1. 開いているコンソールでサインアウトしてから、もう一度「コンソールを開く」          │
│   2. コンソールのマルチセッション（最大 5 つ）を使う ※2                          │
│   3. ブラウザのプロファイルを分ける                                            │

└────────────────────────────────────────────────────────────────────────────┘
```

- 「コンソールを開く」は `POST <team-base>/login` のフォーム送信（hidden に `entry`・`region`・`csrf`）。`target="_blank"` で新しいタブに開き、ポータルは残す [推測: 新しいタブにする方が U3 の入り直しが楽]
- ロールが 1 つだけなら、選択済みで表示する
- email の行は、その行の email を表示する設定のときだけ出す（§5.6）。「コピー」はクリップボードに入れるだけで、Worker に送らない
- セッションの長さは一覧の値（ロールごとの設定。§11.3）を表示するだけで、利用者は変えられない（短くしたいという要望は §12 の未決事項）
- ポータルはコンソールのセッションの有無を知ることができない（別のオリジンの Cookie）。そのため、衝突の案内は常に静的に出す（§6.4）

### 4.4 S3 `aws login` の手順

```
┌────────────────────────────────────────────────────────────────────────────┐
│ ← 戻る   CLI で使う: svc-b-prod / Developer                                  │
├────────────────────────────────────────────────────────────────────────────┤
│ 前提: AWS CLI 2.32.0 以降。このロールのコンソールを、既定のブラウザで開いてあること   │
│                                                                            │
│ 1. コンソールを開く（まだなら）            [コンソールを開く]                     │
│                                                                            │
│ 2. ~/.aws/config に追記する（プロファイル名は変えてよい）           [コピー]      │
│    ┌────────────────────────────────────────────────────────────────────┐  │
│    │ [profile svc-b-prod-developer]                                     │  │
│    │ region = ap-northeast-1                                            │  │
│    └────────────────────────────────────────────────────────────────────┘  │
│                                                                            │
│ 3. 端末で実行する                                                [コピー]      │
│    ┌────────────────────────────────────────────────────────────────────┐  │
│    │ aws login --profile svc-b-prod-developer                           │  │
│    └────────────────────────────────────────────────────────────────────┘  │
│                                                                            │
│ 4. 開いたブラウザで、次のセッションを選ぶ                                       │
│      アカウント xxxx-xxxx-0006 / FederatedDeveloper / console-<email>        │
│    既定のブラウザが別なら、表示された URL を、コンソールを開いたブラウザに貼る        │
│                                                                            │
│ 5. 確かめる:  aws sts get-caller-identity --profile svc-b-prod-developer      │
│                                                                            │
│ 認証情報は 15 分ごとに自動で更新され、最長でセッションの長さ（8 時間 ※）まで使えます。 │
│ 終わったら: aws logout --profile svc-b-prod-developer                         │
│ 端末にブラウザがない環境（--remote）は、既定では使えません。                       │
└────────────────────────────────────────────────────────────────────────────┘
```

- 表示するのは、その行の情報から作った文字列だけ。認証情報・URL・トークンは含まない
- 手順 1 の「コンソールを開く」は、S2 と同じフォームの POST（`POST <team-base>/login`）。S3 にも S2 と同じ CSRF トークンを hidden で入れる（§9.2）
- プロファイル名の既定は `<アカウント名>-<ロール>` を小文字にしたもの。プロファイル名に使えない文字は `-` に置き換える
- `login_session` は書かない。`aws login` が選んだセッションから書き込む [確認済み: AWS CLI の文書。`aws login` が `login_session` を config に書く]
- 「--remote は既定で使えない」は、ロールの権限の作り方に依存する（§6.5）

### 4.6 S4 エラー

| 状況 | 見出し | 本文の要点 | 利用者の次の操作 |
|---|---|---|---|
| STS が拒否（`sts_denied`） | 「このロールに入れませんでした」 | 一覧には表示されていましたが、AWS 側で拒否されました。一覧の更新日時（例 1 日前）。原因は「一覧が古い」「先方の設定が未更新」「権限が外された」のどれかで、ポータルからは区別できません | 問い合わせ先へ。問い合わせに貼る情報: 時刻・チーム・アカウント ID・ロール・要求 ID |
| 一覧にない（`not_listed`） | 「このチームの一覧にないロールです」 | 古いページやブックマークから送られた可能性 | 一覧を開き直す |
| CSRF トークンの期限切れ・不一致（`csrf_failed`） | 「もう一度選んでください」 | 画面を開いてから時間がたった、または別のタブで操作された | S2 を開き直す（リンク） |
| Access のセッションが POST の途中で切れた | 「もう一度選んでください」 | Access の再認証のあと、ブラウザは `GET <team-base>/login` に戻る。この GET では発行しない | S2 を開き直す |
| ログイン URL の 15 分の期限切れ | （AWS の画面） | ポータルは関与しない。通常は即座に送るので起きない。履歴から開いたときに起きる | ポータルからやり直す |
| AWS の一時障害（`temporarily_unavailable`） | 「AWS に接続できませんでした」 | しばらくしてから再試行 | 再試行 |
| issuer が受け付けられない（`upstream_auth_failed`） | 「このアカウントは現在ログインを受け付けていません」 | 設定の不整合か、緊急停止中 | 問い合わせ先へ |
| 停止中（`login_disabled`） | 「ログインを一時停止しています」 | 運用者が停止スイッチを入れている（§10.2） | 案内に従う。break-glass の手順はポータルの外 |
| 利用者 ID が使えない（`identity_unsupported`） | 「このアカウントの利用者名では発行できません」 | email が SourceIdentity・セッション名の制約（2〜64 文字、`[\w+=,.@-]`）に合わない | 問い合わせ先へ |
| 送信が多すぎる（`rate_limited`） | 「少し待ってから」 | — | 待つ |
| 未所属（Access） | （S6。Access のブロック画面） | Worker は関与しない。Custom block pages で「所属は Entra のグループで決まる。申請先は…」を出す | 申請 |

```
├────────────────────────────────────────────────────────────────────────────┤
│ svc-b-prod（xxxx-xxxx-0006） / Developer / チーム: 開発 (dev)                   │
```

### 4.7 S6 未所属（Access のブロック画面。Worker は描かない）

## 5. 一覧のデータ

### 5.1 出どころ（I3）

一覧は **表示用** で、認可の権威ではない。生成は Worker の外（CI か手元の mise タスク）で行い、Worker にはバンドルして渡す。Worker に AWS の読み取り権限を持たせない。

| 情報 | 出どころ | 備考 |
|---|---|---|
| 管理下のアカウント（ID・名前・**email**・状態・所属 OU） | 各 Organization の管理アカウント（または委任管理者）で、読み取り専用のインベントリ用ロールを引き受け、`ListAccounts` と OU の情報を読む（I1）。`ListAccounts` が返す `Account` に `Email`（アカウントに結び付いた email。6〜64 文字）がある [確認済み: Organizations API リファレンスの `Account` 型] | 停止中のアカウントと、管理アカウントは除く。`DescribeAccount` も同じ `Account` 型を返すので、1 件ずつ引き直す必要はない |
| 管理外のアカウント | 配布時の登録（I2。下流の設定ファイルの `organizations[].accounts`。§11.3）。先方に渡したパラメーターと一緒に記録する | 先方の実態とずれうる。**email は先方の `ListAccounts` を読めないので取れない**。先方から教えてもらった場合だけ登録に書く（任意） |
| アカウント → 種類 | 管理下: OU と種類の対応（設定ファイルの `organizations[].kindOus`）。S3 の Organization は設定ファイルのアカウント単位の指定。管理外: 設定ファイルの登録 | |
| 種類 → ロール → 受け付けるチーム | 設定ファイルの `kinds[].assign`（§11。下流の private リポジトリ。StackSets のパラメーターと同じ元） | 一覧と信頼ポリシーが同じ元から作られるので、ずれるのは反映の遅れの間だけ |
| ロール → セッションの長さ・階層 | 設定ファイルの `roles[]`（`sessionSeconds`・`tier`） | 値は下流で決める |
| 境界（管理下 / 管理外の先方）→ issuer | 設定ファイルの `boundaries`（Worker 用には階層ごとに生成。鍵そのものは secret / KMS） | 一覧には境界の識別子だけを入れる |
| 表示用の Organization 名 | 設定ファイルの `organizations[].displayName` | 管理外の先方の名前は顧客名になりうる（§5.4） |

利用者の所属チームは一覧に入れない。**利用者のチーム = 通ってきた Access アプリ（検証した JWT の AUD）** で、Worker の設定の「AUD → チーム」で決める。

### 5.2 形（案）

Standard 用と Admin 用で **別のファイル** を生成し、それぞれのデプロイにだけバンドルする。

```json
{
  "schemaVersion": 1,
  "tier": "standard",
  "generatedAt": "2026-11-10T03:00:00Z",
  "sourceRevision": "<下流リポジトリ（設定ファイル）のコミット>",
  "accounts": [
    {
      "accountId": "<account-id>",
      "name": "svc-b-prod",
      "email": "aws+svc-b-prod@<domain>",
      "orgLabel": "org-main",
      "boundary": "managed",
      "kind": "C",
      "roles": [
        {
          "role": "developer",
          "roleArn": "arn:aws:iam::<account-id>:role/awsbridge-console/std/FederatedDeveloper",
          "teams": ["dev"],
          "sessionSeconds": 28800
        }
      ]
    }
  ]
}
```

| 項目 | 規則 |
|---|---|
| `tier`（ファイル） | `standard` のファイルには設定で `tier: "standard"` のロールだけ、`admin` のファイルには `tier: "admin"` のロールだけを入れる |
| `role` | 設定ファイルの `roles[].name`。前の版はここを `tier` と呼んでいたが、ファイルの `tier`（Standard / Admin）と紛れるので改めた。`entry` とクエリの名前も `role` にそろえる（§12.2 の G-5） |
| `email` | 任意。`inventory.accountEmail`（§11.3）が `hidden` の境界の行には**生成の時点で入れない**（バンドルにも入れない）。`masked` なら伏せた形だけを入れる（§5.6） |
| `roleArn` | パスは、その生成物の階層の `/awsbridge-console/<tier>/`（Standard は `/awsbridge-console/std/`、Admin は `/awsbridge-console/admin/`）に限る。アカウント ID は `accountId` と一致する |
| `teams` | 設定ファイルの `teams` のうち、ファイルと同じ階層のチーム名の部分集合（Admin の行は `tier: "admin"` のチーム。例 `infra-elevated`。§11.3） |
| `boundary` | `managed` または `partner:<識別子>`。Worker の設定の issuer の対応に存在するもの |
| `sessionSeconds` | ロールの MaxSessionDuration 以下（ずれると `getSigninToken` が失敗しうる [資料: PoC で 43200 = MaxSessionDuration は受理された]） |

CI で検査すること（生成のたび）:

- スキーマ。上の規則
- Standard のファイルに Admin の行がない。Admin のファイルに Standard の行がない
- 管理アカウントの行がない
- `teams` が Access の Terraform（チームのアプリ）と Worker の「AUD → チーム」の設定に揃っている（cto の条件: Access ポリシーの形を CI で検査する）。3 つとも設定ファイルから生成するので、この検査は「生成し忘れ・適用し忘れ」を見つけるためのもの（§11.5）
- `hidden` の境界の行に `email` がない

### 5.3 生成と反映

| 項目 | 案 |
|---|---|
| 生成の時機 | 定期（例 1 日 1 回）と、設定ファイルの変更時 [推測: 頻度は要調整] |
| 反映 | 生成物を Worker にバンドルして再デプロイする（MCP 用の `profiles.json` と同じく wrangler の `alias`。§11.2）。KV に置く案は、バンドルが上限に近づいたときに見直す |
| 生成物の置き場所 | 生成物（email を含む）はコミットしない。上流では gitignore、下流でも CI の中で生成してそのままデプロイし、リポジトリに残さない（§5.6） |
| 大きさ | 500 アカウント × 3 ロールで数百 KB 程度 [推測]。Workers のバンドルの上限（architecture.md の記載）に十分収まる |

### 5.4 チームごとの絞り込み

- Worker は、AUD から決めたチームを `teams` に含むロールの行だけを返す。**他のチームの行は HTML にも JSON にも出さない**（サーバー側で絞り込む）
- 理由: 管理外の先方のアカウント名・Organization 名は顧客名になりうる。チームをまたいで全一覧を見せる必要はない
- 入口（S0）でもアカウントの一覧は出さない（最近使ったものは localStorage から出す）
- アカウントの email も同じ絞り込みに従う。表示・検索できるのは、そのチームの行の email だけ（§5.6）

### 5.5 表示と実際の権限がずれたとき

信頼ポリシーが最終判断なので、ずれても権限は広がらない。起きるのは次の 2 つだけ。

| ずれ | 起きること | 主な原因 | 扱い |
|---|---|---|---|
| 表示されるのに拒否される | STS が `AccessDenied`（理由は返らない）→ S4 `sts_denied` | 権限を狭める変更の反映待ち・一覧の生成待ち・管理外の先方の未更新・ロールの削除 | 発行記録に `sts_denied` を残し、アカウントごとの件数を見張る。急に増えたら一覧と StackSets の差を調べる |
| 入れるのに表示されない | ポータルからは入れない | 権限を広げる変更（StackSets の反映）のあと、一覧の生成がまだ | 一覧の再生成を待つ（または手で流す）。**ARN の自由入力は受け付けない**（§12.4） |

ポータルの選択の検証に一覧を使う（一覧にないロールには発行しない）。これは「許可を広げない側」の絞り込みで、権威ではない。cto の制約（一覧は表示用。最終判断は信頼ポリシー）の範囲内と考える [推測: 段階 1 のゲートで確認を求める]。

### 5.6 アカウントの email の扱い

利用者の決定で、アカウントの email（ルートの email）を検索の項目に加えた。email は個人情報になりうるうえ（個人名を含む宛先、顧客のドメイン）、攻撃の手がかりにもなる（ルートのパスワードの再設定・フィッシングの宛先）。ログインに要る情報ではないので、**出す場所を絞り、残さない**。

| 項目 | 方針 |
|---|---|
| 出どころ | 管理下: `ListAccounts` の `Email`（§5.1）。管理外: 先方から教えてもらったものを設定ファイルの登録に書いたときだけ。どちらもないときは空で、検索に当たらない。**手で書いた email は設定ファイルごと下流（private）にコミットされる**（生成物をコミットしない §5.3 の例外）。それを避けたいなら書かない |
| 表示する場所 | **そのチームの行**の S1（2 行目）と S2 だけ。S0・S3・S4・S5 には出さない。他のチームの行の email は、HTML にも埋め込む JSON にも入れない（§5.4 と同じサーバー側の絞り込み） |
| 一覧の応答に含める範囲 | ポータルに JSON の API はない（§9.2）。「一覧の応答」は S1 の HTML に埋め込む JSON のこと。ここに入れる email は境界ごとの設定 `inventory.accountEmail`（§11.3）で決める: `full`（そのまま）/ `masked`（ローカル部の先頭 2 文字だけを残し、`aw***@<domain>` の形。ローカル部が 2 文字以下なら先頭 1 文字）/ `hidden`（入れない）。既定は **管理下・管理外とも `full`（すべて表示）**（Q-P9 の決定）。`masked` と `hidden` は生成の時点で伏せる・落とすので、元の値はバンドルにも入らない。`masked` の行は伏せた形に対してだけ検索が当たる |
| 検索 | ブラウザ内の絞り込みでは、埋め込んだ JSON の email に部分一致（大文字と小文字を区別しない）。JS なしの `?q=` では、要求の URL に検索語が入る。Workers のログや Logpush の要求の記録に URL のクエリが残るか [未検証]（P-7）。残るなら、JS なしの検索は email を対象にせず、案内に「email で探すには JavaScript が要る」と出す |
| ログ | 監査ログ（§10.3）・エラーのログ・例外の文に**アカウントの email を出さない**（アカウント ID で足りる）。`?q=` の値もログに出さない。利用者の email（監査の主体）は従来どおり残す。この 2 つを取り違えない |
| localStorage | お気に入り・最近使ったものに email を入れない（§9.6）。共有端末やブラウザの同期に広がるのを避ける |
| 問い合わせの情報 | S4 の「問い合わせに貼る情報」に入れない（§4.6） |
| バンドルと生成物 | Worker のバンドルには、その階層の全チームの行の email が入る（絞り込みは要求のたびに行うため）。バンドルを読めるのは Cloudflare のアカウントで Workers を読める人。生成物はリポジトリに残さない（§5.3）。上流には実際の email を一切置かない（例は `aws+svc-b-prod@<domain>` の形） |
| Admin のポータル | Standard と同じ規則。Admin のバンドルには Admin の行の email だけが入る |
| 応答ヘッダー | 一覧と詳細は既に `Cache-Control: no-store`（§9.6）。email を含む画面も同じ |

- そのチームの人は、その行のアカウントにログインできる人なので、email を見せても新たに開く範囲は小さいと考える [推測]。ただし、ReadOnly のロールではコンソールでルートの email を見られない場合がある（必要な権限による）[推測] ので、ポータルが見せる範囲の方が広くなりうる。これを避けたい下流は `masked` か `hidden` にする
- 管理外の先方の email も既定で出す（Q-P9 の決定: ポータルを使うのは社員だけで、先方の利用者は使わない前提）。先方の email は先方の情報なので、先方との取り決めで広げられないものは、下流で `partner` を `masked` か `hidden` にするか、登録に書かない

## 6. ログインの流れ

### 6.1 コンソール（シーケンス）

```
ブラウザ          Access（チームのアプリ）      console Worker（Standard）             STS / サインイン（AWS）
  │ POST <team-base>/login │                          │                                   │
  │ (entry, region, csrf)  │                          │                                   │
  │───────────────────────▶│ CF_Authorization を検証    │                                   │
  │                        │ ポリシー: チームの Entra    │                                   │
  │                        │ グループ（Object ID）       │                                   │
  │                        │── Cf-Access-Jwt-Assertion ─▶│                                   │
  │                        │                          │ 1. Access JWT を検証（iss・署名・exp・aud）│
  │                        │                          │ 2. AUD → チーム（未知なら 403。パス・ホストの │
  │                        │                          │    チームと違えば 403）                 │
  │                        │                          │ 3. Origin・Content-Type・CSRF を検査     │
  │                        │                          │ 4. 停止スイッチ・回数の制限                │
  │                        │                          │ 5. entry を一覧で引く（このチームの行だけ）  │
  │                        │                          │    → roleArn・boundary・sessionSeconds │
  │                        │                          │ 6. 境界の issuer の鍵で短命 JWT（~5 分）   │
  │                        │                          │    sub=email、awsbridge_team=<チーム>、   │
  │                        │                          │    source_identity=<email>            │
  │                        │                          │── AssumeRoleWithWebIdentity ─────────▶│
  │                        │                          │   (RoleSessionName=console-<email>)   │ 信頼ポリシー:
  │                        │                          │◀── 一時認証情報 ────────────────────────│ aud・RequestTag・
  │                        │                          │── getSigninToken (SessionDuration) ──▶│ TagKeys・SI 必須
  │                        │                          │◀── SigninToken ───────────────────────│
  │                        │                          │ 7. 発行記録（URL・認証情報は書かない）       │
  │◀──────────── 302 Location: federation?Action=login&Issuer=…&Destination=…&SigninToken=… ──│
  │─────────────────────────────────────────────────────────────────────────────────────────▶│
  │◀──────────────────────────────────────────────── コンソール（S8）────────────────────────│
```

- 一時認証情報は Worker の中だけで使い、ブラウザに渡さない。キャッシュもしない（使い捨て）
- `RoleSessionName` は `console-<email>` とし、同じ人が同じロールに入り直すとセッション名が変わらないようにする（S3 の手順でセッションを見分けやすくするため）。接頭辞 `console-`（8 文字）と RoleSessionName の上限 64 文字から、email は 56 文字まで。email が制約に合わなければ `identity_unsupported` [資料: SourceIdentity の制約]
- `DurationSeconds` は指定しない（または `sessionSeconds` と同じ）。PoC では DurationSeconds=43200 と SessionDuration の組み合わせでも `getSigninToken` が通った [確認済み: PoC の A-4〜A-6。ログインは試していない]

### 6.2 ログイン URL の渡し方: 302 と POST

AWS の文書は、ログイン URL を秘密として扱い、302 で渡すことを勧めている。`Action=login` は POST でも受け付ける [確認済み: AWS の文書]。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **T1 302**（第一案） | `Location` に `Action=login` の URL を入れる | AWS の推奨。PoC で URL を開いてコンソールに入れた [確認済み: A-2] | URL がブラウザの履歴に残る（15 分有効）。拡張機能や画面共有から見えうる |
| T2 自動送信の POST | `Action=login`・`Issuer`・`Destination`・`SigninToken` を hidden に入れたフォームを返し、nonce つきのスクリプトで送信する（スクリプトがなければボタン） | トークンが URL・履歴・`Referer` に出ない | 応答の HTML にトークンが入る（`no-store` が要る）。**ポータルからの POST でログインできるかは未検証** |

- 段階 1 は T1 で始め、T2 を PoC（P-4）で確かめてから切り替えを検討する
- `SigninToken` が 1 回使うと無効になるかは、文書に記載がない [未検証]

### 6.3 `Issuer` と `Destination`

| パラメーター | 値 | 作り方 |
|---|---|---|
| `Issuer` | `<team-base>/expired` | 設定ファイルの `portal.standardOrigin`（Admin は `adminOrigin`）とチームから作る。**要求の値（`Host` ヘッダーを含む）を使わない**。OIDC の issuer とは別物（§3.1） |
| `Destination` | `https://<region>.console.aws.amazon.com/console/home?region=<region>` | `<region>` は許可リスト（設定ファイルの `portal.regions`）にあるものだけ。リストにない値は既定のリージョンに置き換える。**URL を利用者から受け取らない** |
| フェデレーションのエンドポイント | `https://signin.aws.amazon.com/federation`（または `https://<region>.signin.aws.amazon.com/federation`） | 設定で固定。リージョンの選択は可用性の観点で見直す [推測] |

特定のサービスの画面に直接入る（`Destination` にサービスのパスを付ける）機能は、許可リスト方式でなら足せる。当面は持たない。

### 6.4 既存のコンソールのセッションとの衝突とマルチセッション

PoC で分かったこと: 同じブラウザに別のフェデレーションのコンソールのセッションが残っていると、新しいログイン URL を開いても切り替わらない [確認済み: PoC の運用上の注意]。PoC のときにマルチセッションが有効だったかは記録がない。

N10 の実測（2026-11-11）: 前の PoC で消したロールのコンソールのセッションがブラウザに残っていると、新しいログイン URL が「Credentials invalid」になった。コンソールからサインアウトすると通った [確認済み: 開発環境の PoC]。そのため、S2 の「切り替わらないとき」の案内には、症状が「切り替わらない」だけでなく「Credentials invalid」になることがある（特に消えたロールのセッションが残っているとき）と書き、サインアウトしてからやり直す導線を置く。

AWS の文書で分かること:

- コンソールは 1 つのブラウザで最大 5 つの ID に同時にサインインできる。対象は root・IAM・フェデレーションのロールの組み合わせ。マルチセッションはブラウザごとのオプトインで、有効にするとコンソールの URL にサブドメインが付く [確認済み: AWS の文書]
- 文書の手順は、追加のロールへのフェデレーションについて「IAM Identity Center のアクセスポータルか、SSO のポータルで追加のロールにサインインし、コンソールのアカウント名から追加のセッションを見る」とだけ書く [確認済み: 同じ文書]。**カスタムの ID ブローカー（`getSigninToken` の URL）で入ったときに追加のセッションになるか、6 つ目はどうなるかは書かれていない**（未確認。P-1 で確かめる）
- コンソールのサインアウトの URL（ログイン URL の前に挟めるもの）は、読んだ公式文書には書かれていない（未確認。非公式に知られた URL を前提にしない）

ポータルはコンソールのセッションの状態を知ることができない（別のオリジン）。そのため、設計は次のようにする。

| 段階 | 対応 |
|---|---|
| 段階 1（今の知見） | S2 に「切り替わらないとき」の案内を常に出す（サインアウトしてからやり直す・マルチセッション・ブラウザのプロファイル）。新しいタブで開くので、ポータルは残る |
| P-1 の結果でマルチセッションの追加に使えると分かったら | 案内の 1 番目をマルチセッションにし、有効にする手順を S2 とヘルプに出す |
| P-1 で公式のサインアウトの手順（URL かコンソールの操作）とその後の遷移が確かめられたら | 「サインアウトしてから開く」ボタンを足すか検討する |

### 6.5 `aws login`

ポータルが行うのは S3 の案内だけで、CLI のための仕組み（認証情報の発行・`credential_process`）は持たない。

| 項目 | 内容 | 状態 |
|---|---|---|
| 必要な権限 | `signin:AuthorizeOAuth2Access` と `signin:CreateOAuth2Token`。対象のリソースは `arn:aws:signin:<region>:<account-id>:oauth2/public-client/localhost`（同じ端末の `aws login`）と `.../remote`（`aws login --remote`） | [確認済み: AWS の文書] |
| `--remote` を既定で許さない | AWS 管理ポリシー `SignInLocalDevelopmentAccess` は `localhost` と `remote` の両方を許す。そのため、**ロールのテンプレートでは管理ポリシーを付けず、`localhost` だけを許すポリシーを付ける**（管理下では SCP で `remote` を拒否する案もある） | 設計。テンプレートへの依存として §12 に挙げる |
| 同じ端末の `aws login`（フェデレーションのセッションから） | PoC で確かめたのは `--remote` だけ。既定のブラウザが PoC のプロファイルでなかったため [確認済み: PoC の B-2] | **未検証**（P-2） |
| ブラウザでのセッションの選択 | アクティブなセッションの一覧から選ぶ。マルチセッションが有効なら最大 5 つから選べる。コンソールにまだ入っていなければ、別のタブで入ってから「更新」を押す | [確認済み: AWS の文書（AWS Security Blog）] |
| 長さ | 認証情報は 15 分ごとに更新され、ロールのセッションの長さ（最大 12 時間）まで使える。Admin はロールの MaxSessionDuration を短くするので、`aws login` も短くなる | [確認済み: AWS の文書と PoC（15 分の更新）]。長さの上限は段階 3 前の PoC（cto の N2）で確かめる |
| 停止 | Revoke Sessions で `aws login` の更新も止まった | [確認済み: PoC の P4(a)] |

## 7. 複数のチームに所属する人

M2 では、Worker は利用者の所属を知らない。チームは「どの Access アプリを通ってきたか」で決まる。

| 場面 | 見え方 |
|---|---|
| チームを選ぶ | S0 で全チームを並べる。所属していないチームを選ぶと、Access のブロック画面（S6）になる |
| 自分が入れるチームを知る | Access の App Launcher（`https://<team-name>.cloudflareaccess.com`）は、利用者が使えるアプリのタイルを表示する [確認済み: Cloudflare の文書（RDP の手順の記載）]。チームのアプリを App Launcher に出せば、所属の確認に使える。ポータルは App Launcher へのリンクを置くだけで、所属を調べない |
| チームを切り替える | ヘッダーの「チーム ▼」から別のチームの S1 に移る。Access は、そのチームのアプリのポリシーで判定し直す。2 つ目以降のアプリで再ログインは要らなかった（IdP のグローバルセッションが共有される）[確認済み: 開発環境の PoC の M2。Google の IdP]。R-P で Cookie Path を無効にしていると、切り替えのたびに Cookie が上書きされ、Access への往復が起きうる [推測] |
| 同じアカウントに複数のチームで入れる | チームごとに入れるロールが違う（例 種類 B: Admin の階層の `dev-elevated` は Admin、`sa` は ReadOnly。§11.3 の例）。S1・S2 は、今のチームのロールだけを表示する。どのチームを選んでも権限はロールで決まる（権限ポリシーで `aws:PrincipalTag/awsbridge_team` を使わない）[資料: 設計上申 §4.6.5] |
| 所属の変更が効くまで | ポリシーから外すだけでは、発行済みのアプリのトークン（アプリのセッション時間。PoC の infra は 24 時間）は使い続けられる。外したあと、(1) ポリシーの変更が Access に伝わるのを待つ（PoC では約 20 秒で失効させても新しいトークンが発行され、約 2 分 15 秒後の失効では拒否された）、(2) アプリのトークンを失効させる（`revoke_tokens`）か、期限切れを待つ（期限切れのときにポリシーが判定し直され、IdP の再ログインなしに拒否された）。即時に効く保証はないので、運用の手順は固定の待ち時間ではなく「ポリシー変更 → 失効 → **拒否されたことを確かめて完了**」とし、セッション時間は短くする（推奨値は [console-login.md](console-login.md) §6.4。発行済みの AWS のセッションは止まらないので、止めるにはロールの revoke か、1 人なら `aws:SourceIdentity` の Deny（測定中。console-login.md §6.1 の L3-1））[確認済み: 開発環境の PoC の N10。Google の IdP。Entra のグループで同じかは会社環境で確かめる（N1・N10 の残り）] |
| CloudTrail | 引き受けのイベントにタグ `awsbridge_team` が残る [確認済み: PoC の P3（`access_profile` で確認）]。「どのチームの立場で入ったか」が分かる |
| 最近使ったもの | localStorage にチームと一緒に記録する。S0 では全チーム分を出し、開くとそのチームの S2 へ移る（R-P の場合） |
| 一覧で見つからない | 他のチームで同じ検索語を開くリンクを出す（中身は見せない） |

M3（Worker が所属の一覧を得て和集合を表示する）は、N1 で完全なグループ一覧が取れると分かった場合の比較対象で、この設計には含めない。

## 8. Admin と Standard の分離

cto の決裁により、Admin の issuer は Standard と別の Worker デプロイになる。画面にも 2 つのポータルとして現れる。

| 項目 | Standard | Admin |
|---|---|---|
| URL（例） | `https://portal.<domain>/` | `https://admin-portal.<domain>/`（別のオリジン） |
| Worker | Standard のデプロイ | Admin のデプロイ（別のエントリか、同じエントリの別設定。§9.10） |
| Access アプリ | 入口 + 設定ファイルの `tier: "standard"` のチームごと（例 `infra` / `dev` / `sa`） | 入口 + `tier: "admin"` のチームごと（例 `infra-elevated`。PIM のグループ。段階 3 で決める） |
| Access のセッション | 長め（値は未定） | 短く。ログインのたびに再認証を求める案を検討する |
| 一覧 | Developer・ReadOnly の行だけ | Admin の行だけ |
| issuer と鍵 | Standard の鍵（段階 1・2 は Workers secret。境界ごと） | Admin の鍵（KMS 必須。境界ごと） |
| 見た目 | 通常の配色 | 警告色の帯・`[ADMIN]` の見出しとタブのタイトル・確認の文 |
| 互いの関係 | Admin ポータルへの**静的なリンク**だけを置く。Admin の行は表示しない | Standard ポータルへの静的なリンクだけを置く |

決めたこと:

- **Standard の一覧には Admin の行を出さない**（「Admin もあります」の件数も出さない）。出すには Admin のデータを Standard のバンドルに入れることになり、「Standard のデプロイに Admin の情報を入れない」という分離が崩れる
- Admin の行を Standard から選んで Admin に送る仕組みは作らない。利用者は Admin ポータルで改めて探す
- 2 つのポータルは別のオリジンなので、お気に入り・最近使ったもの（localStorage）は共有されない
- Admin のポータルは段階 3 まで存在しない。段階 1・2 では Standard だけを公開する

## 9. エンドポイントとセキュリティ

### 9.1 Access アプリとの対応

| Access アプリ | 対象（R-P の場合） | ポリシー | AUD の扱い |
|---|---|---|---|
| 入口 | `portal.<domain>/`（チームのパス以外） | チームの Entra グループのどれかに所属（Object ID。和集合） | 既知だが、**どのチームにも対応しない**。この AUD では発行しない |
| チーム `<team>` | `portal.<domain>/t/<team>/` | そのチームの Entra グループ（Object ID） | AUD → `<team>`。Terraform の出力から Worker 用の設定に生成する（§11.4） |
| issuer の公開文書 | `/.well-known/...`（パスは issuer の分け方で決まる。N9） | Bypass（IAM が読む）。**issuer を専用ホストに置く案（[console-login.md](console-login.md) §3.1）ならポータルのホストには不要** | — |

- Access の Cookie の設定（推奨）: Binding cookie を有効にする。HttpOnly は既定のまま有効。SameSite は Lax（Strict はリダイレクトの繰り返しを起こしうると文書にある）。R-P では Cookie Path を有効にし、チームごとに Cookie を分ける [確認済み: Cloudflare の文書に各設定の説明。組み合わせの動作は未検証（N1）]
- **CSRF の対策は Access の Cookie の SameSite に頼らない**（既定は None で、設定に依存するため）
- Access ポリシーの形（チームのアプリが、そのチームのグループの Object ID だけを要求していること）は CI で検査する [資料: cto の条件]
- この表のアプリ（入口・チームごと・Bypass。Bypass は issuer をポータルのホストに置く場合だけ。専用ホスト案なら不要。console-login.md §3.1）は、下流の設定ファイルの `portal` と `teams` から Terraform で作る（`for_each`）。アプリのドメインは自社ドメインのポータルのホスト（§3.1）。チームを足すのは設定ファイルに 1 件足すだけで、Terraform と Worker の対応が同時に変わる（§11.4）

### 9.2 エンドポイント

パスは R-P の場合。R-H では `<team-base>` の部分がホストになる。

| パス | メソッド | Access アプリ | 入力 | 出力 |
|---|---|---|---|---|
| `/` | GET | 入口 | — | S0（HTML）。チームのリンク、ヘルプ |
| `/t/<team>/` | GET | チーム | クエリ `q`・`org`・`kind`・`role`・`boundary`・`page`（すべて任意。許可リストと長さで検査） | S1（HTML）。そのチームの行を埋め込む（§10.1） |
| `/t/<team>/a/<account-id>` | GET | チーム | クエリ `role`（任意） | S2（HTML）。CSRF トークンを hidden に入れる |
| `/t/<team>/a/<account-id>/cli` | GET | チーム | クエリ `role` | S3（HTML）。「コンソールを開く」用に CSRF トークンを hidden に入れる |
| `/t/<team>/login` | POST | チーム | `application/x-www-form-urlencoded`: `entry`（`<account-id>:<role>`。`<role>` は設定の `roles[].name`）・`region`・`csrf` | 302（フェデレーション）または S4 |
| `/t/<team>/login` | GET | チーム | — | 「もう一度選んでください」（Access の再認証のあとに戻る先）。**発行しない** |
| `/t/<team>/expired` | GET | チーム | — | S5 |
| `/assets/*` と `/t/<team>/assets/*` | GET | 入口 / チーム | — | 静的なファイル（CSS・JS）。秘密を含まない。**チームのページはチームのパスの下から読む**（R-P で Cookie Path を有効にすると、チームの S1 をブックマークから開いた人は入口のアプリの Cookie を持たず、`/assets/*` が Access に転送されるため）。中身は同じファイル |
| issuer の discovery と JWKS | GET | Bypass | — | MCP 用と同じ形。issuer のパスとホストは N9 で決める（この文書の範囲外）。専用ホスト案（console-login.md §3.1）ならポータルの Worker はこの経路を持たない |

- JSON の API は持たない（一覧は HTML に埋め込む）。外から叩ける面を減らすため。email の検索のために API を足すこともしない（§5.6）
- `q` には email が入りうる。値をログに出さない（§9.9）
- `<account-id>` は 12 桁の数字だけを受け付ける。`<team>` は設定にあるチーム名だけ
- `HEAD` は `GET` と同じ。ほかのメソッドは 405

### 9.3 `POST /t/<team>/login` の検査の順

本文を読む前に 1〜3、STS を呼ぶ前に 4〜8 を判定する。どこかで失敗したら発行しない（fail-closed）。

1. Access JWT を検証する（iss = チームドメイン、署名、exp、aud）。失敗は 401
2. AUD → チーム。`aud` はちょうど 1 つの値で、既知のチームの AUD であること。`aud` が複数（配列に 2 つ以上）・空・未知、または複数のチームに当たる曖昧な組み合わせなら 403 `unknown_audience`（警告のログ）。入口の AUD も 403。パスのチームと違えば 403 `team_mismatch`。AUD → チームの対応は表示用ではなく**認可の設定**として扱う（[console-login.md](console-login.md) §5.1 の A12）
3. `Origin` が**あり**、かつポータルのオリジン（設定ファイルの `portal.standardOrigin` または `adminOrigin`）と完全一致すること。`Sec-Fetch-Site` があれば `same-origin` であること。違えば 403 `forbidden_origin`（MCP 用は `Origin` がなければ通すが、ポータルは**なければ拒否**する）。Content-Type が `application/x-www-form-urlencoded` でなければ 415
4. CSRF トークンを検証する（§9.5）。失敗は 403 `csrf_failed`
5. 停止スイッチ（§10.2）が入っていれば 503 `login_disabled`
6. 回数の制限（利用者ごと）。超えたら 429 `rate_limited`
7. `entry` を一覧で引き、**このチームの行で、このデプロイの階層のもの**であることを確かめる。なければ 404 `not_listed`。`region` は許可リストにあるもの（なければ既定）
8. email が SourceIdentity とセッション名の制約に合うこと。合わなければ 403 `identity_unsupported`
9. 署名 → STS → `getSigninToken` → 発行記録 → 302

- 判定に使う値（JWT・設定・一覧）が読めない・壊れている・想定外の形のときは、すべて発行しない側に倒す（fail-closed）。例外を握りつぶして続行しない
- Access JWT の検証は署名と期限だけを見るので、失効させた Access のトークン（JWT）を Access を経由せずに直接持ち込まれると、期限内なら検証を通りうる [資料: Sol のレビューの指摘 2]。そのため、**Access を経由しない入口を閉じる**ことを前提にする（[console-login.md](console-login.md) §5.4 の「Access を経由しない入口」）。Worker は Access の再評価を代わりにしない

### 9.4 エラーと HTTP ステータス

architecture.md の形に合わせる。ポータルは HTML を返すが、`code` は画面の要求 ID と一緒に表示し、ログにも残す。内部の詳細（STS の本文、例外の文）は画面に出さない。

| 状況 | HTTP | code |
|---|---|---|
| Access JWT がない・不正 | 401 | `unauthorized` |
| 未知の AUD・入口の AUD で発行しようとした | 403 | `unknown_audience` |
| パス（ホスト）のチームと AUD のチームが違う | 403 | `team_mismatch` |
| `Origin` がない・違う、`Sec-Fetch-Site` が `same-origin` でない | 403 | `forbidden_origin` |
| Content-Type が違う | 415 | `unsupported_media_type` |
| CSRF トークンがない・不正・期限切れ | 403 | `csrf_failed` |
| 停止スイッチ | 503 | `login_disabled` |
| 回数の制限 | 429 | `rate_limited` |
| 一覧にない `entry`・階層の違い | 404 | `not_listed` |
| email が制約に合わない | 403 | `identity_unsupported` |
| STS が `AccessDenied` | 403 | `sts_denied` |
| STS が JWT を拒否（`InvalidIdentityToken` など） | 502 | `upstream_auth_failed` |
| STS・サインインの一時障害 | 503 | `temporarily_unavailable` |
| `getSigninToken` の失敗 | 502 | `signin_failed` |
| 設定の欠落・一覧の不正・鍵の不正 | 500 | `server_misconfigured` |

### 9.5 CSRF

前提: ポータルはブラウザが主な利用者で、Access の Cookie で認証される。ログインは画面の遷移（AWS への送り出し）で終わるので、`fetch` ではなく**通常のフォームの POST** にする。したがって、トークンは独自ヘッダーではなく hidden のフィールドで送る。

| 対策 | 内容 |
|---|---|
| GET で発行しない | 発行は `POST <team-base>/login` だけ。`GET <team-base>/login` は案内だけ |
| Origin の必須化 | §9.3 の 3 |
| CSRF トークン | 状態を持たない署名つきトークン。`HMAC-SHA256(csrf_key, version | AUD | sub | 発行時刻)` と発行時刻を S2 の hidden に入れ、POST で検証する。有効期限は短く（例 10 分）[推測: 値は要調整]。`csrf_key` は署名鍵と別の Worker secret。**AUD に束縛する**ので、R-P で同じオリジンにある別のチームのページのトークンは使えない |
| 画面の埋め込み | `Content-Security-Policy: frame-ancestors 'none'` でクリックジャッキングを防ぐ |
| Content-Type | §9.3 の 3 |

却下: Cookie の二重送信（ポータルが自前の Cookie を持つことになる）、SameSite だけに頼る（Access の設定に依存する）。

### 9.6 Cookie と応答ヘッダー

| 項目 | 内容 |
|---|---|
| ポータル自身の Cookie | **持たない**。認証は Access の Cookie、個人の設定は localStorage |
| `Cache-Control` | すべての応答で `no-store`（静的なファイルを除く） |
| `Referrer-Policy` | `same-origin`。AWS への遷移（別のオリジン）では `Referer` を送らない。`no-referrer` にしないのは、Fetch の仕様では `no-referrer` のページからの GET・HEAD 以外のフォーム送信で `Origin: null` になり、§9.3 の 3（Origin の一致）で自分の POST まで拒否してしまうため [推測: 仕様の読み。実ブラウザでは P-4 で確かめる]。T2 で AWS に POST するときは `Origin: null` になる見込みで、AWS が受け付けるかも P-4 で確かめる |
| `Content-Security-Policy` | `default-src 'self'`、スクリプトは `'self'`（T2 を採るなら nonce）、`frame-ancestors 'none'`、`form-action 'self' https://signin.aws.amazon.com https://*.signin.aws.amazon.com https://console.aws.amazon.com https://*.console.aws.amazon.com`。`form-action` はフォーム送信後のリダイレクトの連鎖すべてに当たるため、サインインからコンソールへのリダイレクト先まで許す必要がある [確認済み: PoC の N10。signin だけだとコンソールへの遷移が止まった] |
| `X-Content-Type-Options` | `nosniff` |
| localStorage に置くもの | お気に入り・最近使ったもの（チーム・アカウント ID・アカウント名・ロール・時刻。**アカウントの email は置かない**。§5.6）、入れたことのあるチーム、リージョンの選択。認証情報・URL・トークンは置かない。消去のボタンを用意する |

### 9.7 オープンリダイレクトの防止

| 遷移先 | 方針 |
|---|---|
| 302 の `Location` | フェデレーションのエンドポイント（設定の固定値）だけ。ポータル内の遷移は相対パスの固定値 |
| `Issuer` | 設定のポータルの URL とチーム名から作る固定値（§6.3） |
| `Destination` | 許可リストのリージョンから作る固定の形（§6.3） |
| 「戻り先」パラメーター | 持たない（`?next=` のような値を受け付けない） |

### 9.8 ログイン URL の扱い

- 作るのは Worker の中だけ。画面に表示しない。コピーのボタンを作らない
- 302（T1）の `Location`、または T2 の hidden にだけ入れる。どちらも `Cache-Control: no-store`
- ログ・例外の文・エラー画面に出さない
- URL の有効期限は 15 分 [確認済み: AWS の文書]。STS の認証情報は URL の外に出ない（URL に含まれるのはサインイントークン）

### 9.9 ログに出さないもの

| 出さない | 理由 |
|---|---|
| ログイン URL・`SigninToken` | セッションそのもの |
| STS の一時認証情報 | 同上 |
| Worker が署名した JWT（完全な形） | 5 分間、引き受けに使える。`jti` と claim の要約だけを残す |
| Access JWT・`CF_Authorization` | Access のセッション |
| CSRF トークン | 再利用を防ぐ |
| STS・サインインの応答の本文 | 認証情報を含む |
| アカウントの email・検索語（`q`） | 個人情報・攻撃の手がかりになりうる。アカウント ID で足りる（§5.6） |

**利用者の** email は監査に要るので残す（ログの置き場所とアクセス権で守る。§10.3）。**アカウントの** email は残さない。

### 9.10 バンドルの分離をテストで確かめる

cto の条件（MCP 用 Worker のバンドルにコンソールログイン用の経路が入らないこと）に加え、Standard と Admin の分離も確かめる。

| テスト | 確かめること |
|---|---|
| MCP 用のバンドル | コンソールログイン用の経路（`/t/`・`/login` など）とモジュールが含まれない |
| Standard のバンドル | Admin の一覧の行・Admin の鍵の参照・Admin のチームの AUD が含まれない |
| Admin のバンドル | Standard の一覧の行が含まれない |
| 設定の読み込み | Standard のデプロイに Admin の階層の行・チーム・issuer が渡されたら、起動時（初回の要求時）に `server_misconfigured` で止まる（生成の段階でも弾く。§11.6） |
| 設定の分離 | Worker 用の生成物に、種類の定義（`kinds`）・Entra のグループの Object ID・他の階層の AUD が入っていない |

実装済みのもの（§11 の設定の実装と一緒に入れた）: MCP 用のバンドルの検査（`test/e2e/console-bundle.test.ts`。`wrangler deploy --dry-run` の metafile の inputs に `src/console/` がなく、本文にタグのキー・audience（`awsbridge-console`）・ロールのパスの接頭辞・`/t/` がないこと。`test/unit/console-layout.test.ts` は `src/index.ts` からの静的な import をたどる）と、設定の分離（`test/unit/console-generate.test.ts`）。Standard・Admin のバンドルと設定の読み込みの検査は、ポータル本体と一緒に足す。

## 11. 設定ファイル: チーム・ロール・種類の定義（上流はスキーマと例、実際の値は下流）

### 11.1 方針と上流・下流の分担

「どんなチームがいて、どんなロールを用意し、どの種類のアカウントでどのチームがどのロールに入れるか」は、組織ごとに違う。awsbridge は OSS（public）なので、上流に会社の値を置けない。そこで、これらは 1 つの**設定ファイル**で定義する。上流はスキーマ・例・生成と検査の道具だけを持ち、実際の値は下流リポジトリ（会社用・個人用）に置く（§0 の利用者の決定）。

| 持ち主 | 持つもの | 持たないもの |
|---|---|---|
| 上流（awsbridge。public） | 設定ファイルのスキーマ（`src/console/config.ts` の型と検証。JSON Schema のファイルは置かない）。例（個人用の最小構成 `config/console.example.json` と、会社用を想定した `config/console.company.example.json`。値はすべてダミー）。生成と検査の道具（mise のタスク）。固定の約束（audience `awsbridge-console`、ロールのパス `/awsbridge-console/<tier>/`、タグのキー `awsbridge_team`、`aws login` は `localhost` だけを許すポリシーを全ロールに付けること。§6.5） | 実際のチーム名・Entra のグループ・AUD・アカウント ID・OU・ドメイン・email |
| 下流（private） | 設定ファイルの実物（例 `deploy/console.json`）、自前の wrangler の設定、Terraform のルートモジュール、CODEOWNERS | 上流のファイルの編集（architecture.md「下流リポジトリでの運用」と同じく、ファイルを足すだけ） |

- 会社用の下流リポジトリ（Q-P10 で決定）は、cto の条件にある「種類の定義を管理する private リポジトリ」そのものである。設計上申で `patterns.yaml` と呼んでいたファイルは、この設定ファイルの `kinds` に当たる（この文書では設定ファイルに一本化する）
- 前の版で利用者への確認事項にしていた「インフラにも ReadOnly を許すか」（旧 Q-P1）は、上流では決めない。下流の設定の `kinds[].assign` で決める（§11.8）

### 11.2 置き場所とバンドルの流れ（profiles.json との比較）

```
下流: deploy/console.json（コミットする。レビューを通す）
   │
   ├─▶ Terraform（for_each で Access アプリとポリシー）──▶ 出力: チーム → AUD
   │                                                        │
   ├─▶ mise run console:config:generate（検査と生成）◀──────────┘
   │      │  + インベントリ（ListAccounts など。§5.1）
   │      ├─▶ .generated/console/worker.standard.json ──alias──▶ Standard の Worker
   │      ├─▶ .generated/console/worker.admin.json    ──alias──▶ Admin の Worker
   │      ├─▶ .generated/console/stacksets.json（パラメーター）──▶ StackSets（CI）
   │      └─▶ .generated/console/access.json（Terraform との突き合わせ用）──▶ CI の検査
   │
   └─▶ mise run console:config:check（PR の検査。AUD なしで通す。生成物は書かない）
```

| 観点 | MCP 用の `profiles.json` | コンソールログイン用の設定ファイル |
|---|---|---|
| 上流に置くもの | `config/profiles.example.json`（ダミー） | `config/console.example.json`・`config/console.company.example.json`（ダミー）と、スキーマ・生成の道具（`src/console/`・`scripts/console/config.ts`） |
| 上流の開発用の実物 | `config/profiles.json`（gitignore。例をコピーして作る） | `config/console.json`（gitignore。例をコピーして作る） |
| 下流 | 自前の JSON に、自前の `wrangler.<name>.jsonc` の `alias` を向ける | 自前の JSON（例 `deploy/console.json`）を、`mise.<name>.toml` の `AWSBRIDGE_CONSOLE_CONFIG` で生成のタスクに渡す。自前の `wrangler.<name>-console.jsonc` の `alias` は**生成物**に向ける |
| Worker に入るもの | ファイルそのもの | **生成物**: その階層のチーム・ロール・境界の issuer と、その階層の一覧の行だけ。`kinds`（種類 × チーム → ロールの表）・Entra のグループの Object ID・Access のポリシー ID・権限ポリシー・他の階層の AUD は入れない |
| ファイルがないとき | wrangler の alias の解決エラー（ビルドが失敗する） | 同じ。加えて、生成のタスクが入力の欠落でエラーになる |
| 読む道具 | Worker だけ | Worker（生成物）・Terraform・StackSets の生成・インベントリの生成・CI の検査 |

生成物を挟む理由:

- ファイルをそのままバンドルすると、Standard のバンドルに Admin の AUD と、種類 × チーム → ロールの表が入る。前者は §9.10 の分離に、後者は cto の制約（Worker は対応表を権威として持たない）に反する
- AUD は Access アプリを作ったときに Cloudflare が決める値で、設定ファイルに先に書けない（§11.4）

タスク名は `console:config:check` / `console:config:generate`、生成物の置き場所は `.generated/console/`（gitignore。`AWSBRIDGE_CONSOLE_OUT_DIR` で変えられる）に決めた。入力は環境変数で渡す: 設定ファイル `AWSBRIDGE_CONSOLE_CONFIG`（既定 `config/console.json`）、Terraform の出力 `AWSBRIDGE_CONSOLE_AUD_FILE`（`{ "teams": { <チーム>: <AUD> }, "entry": { "standard": <AUD>, "admin": <AUD> } }`。`terraform output -json` の値をこの形にする）、インベントリ `AWSBRIDGE_CONSOLE_INVENTORY_FILE`（`{ <Organization>: [{ "accountId", "name", "email"?, "ouPath": [<ルートから親までの ID>], "status"? }] }`）、生成物に記録するコミット `AWSBRIDGE_CONSOLE_SOURCE_REVISION`。Worker が生成物を読むモジュール名（例 `awsbridge:console`）はポータル本体の実装で決める。生成物と、email を含むインベントリはコミットしない（§5.3・§5.6）。生成物はファイルの権限を 0600 にする。

### 11.3 スキーマ（案）と例

#### 項目

| 項目 | 必須 | 内容と規則 |
|---|---|---|
| `schemaVersion` | 必須 | `1`。上流と下流の契約の版。互換性のない変更で上げ、移行の手順を上流の文書に書く |
| `portal.standardOrigin` | 必須 | Standard のポータルのオリジン（`https://<host>`。パスなし）。自社ドメインのホスト。`workers.dev` は受け付けない（§3.1） |
| `portal.adminOrigin` | Admin の階層のチームかロールがあれば必須 | Admin のポータルのオリジン。`standardOrigin` と違うこと |
| `portal.routing` | 任意（既定 `path`） | `path`（R-P）/ `host`（R-H）。§3.1・G-1 |
| `portal.regions` | 任意 | `allowed`（リージョンの配列）と `default`。省略するとリージョンの選択を出さず、`Destination` にリージョンを付けない |
| `portal.supportUrl` | 任意 | 問い合わせ先（S1・S4 のリンク。旧 Q-P6） |
| `portal.entryAud` | 任意 | 入口のアプリの AUD。階層ごと（`{ "standard": ..., "admin": ... }`。Standard と Admin のポータルはそれぞれ入口のアプリを持つ。§8）。Terraform を使わず、その階層のチームが 2 つ以上のときだけ手書きする（Terraform なら出力から入る。チームが 1 つなら入口のアプリは要らない。§11.7） |
| `teams[]` | 1 件以上 | チーム。`name` は `^[a-z][a-z0-9-]{0,31}$`（タグの値・URL のパス・Access アプリの名前に使う）。`displayName`（任意。既定は `name`）。`tier`（`standard` / `admin`。既定 `standard`）。`access` は Access のポリシーの元で、Terraform で作るなら `groupObjectIds`（Entra のグループの Object ID。会社用）か `policyIds`（既存の再利用できるポリシーの ID）のどちらか一方。Terraform を使わない構成では、手で作ったアプリの `access.aud` だけを書く（§11.4・§11.7） |
| `roles[]` | 1 件以上 | ロール。`name`（`^[a-z][a-z0-9-]{0,31}$`。一覧・`entry`・`kinds` で使う）。`roleName`（IAM のロール名。パスは階層で決まる `/awsbridge-console/<tier>/` に固定。`<tier>` は `std` / `admin`）。`displayName`（任意）。`tier`（既定 `standard`）。`sessionSeconds`（900〜43200。MaxSessionDuration と一覧の表示に使う。旧 Q-P2）。`permissions.managedPolicyArns`（AWS 管理ポリシーの ARN）と `permissions.inlinePolicyFiles`（下流のポリシー文書のパス。任意） |
| `kinds[]` | 1 件以上 | アカウントの種類。`name`、`displayName`（任意）、`assign`（`{ <ロールの name>: [<チームの name>, ...] }`）。**割り当てるチームとロールの `tier` は一致すること**（Admin のロールは Admin の階層のチームだけを受け付ける） |
| `boundaries[]` | 1 件以上 | 信頼の境界。`name`（`managed` か `partner:<識別子>`）と `issuers`（`standard` と、Admin を使うなら `admin` の issuer の URL）。issuer のホストとパスは N9 で決める。鍵そのものは書かない（secret / KMS） |
| `organizations[]` | 1 件以上 | アカウントの出どころ。`name`・`displayName`・`boundary`・`placement`（`ou` = S1 / `accounts` = S3 と管理外・単独のアカウント）。`ou` では `inventoryRoleArn`（`ListAccounts` を読むロール）と `kindOus`（`{ <種類>: [<OU ID>, ...] }`）。`accounts` では `accounts[]`（`accountId`・`name`・`kind`・`email`（任意）） |
| `inventory.accountEmail` | 任意 | 一覧に入れるアカウントの email。`{ "managed": "full" \| "masked" \| "hidden", "partner": ... }`。既定は `managed: full`、`partner: full`（すべて表示。Q-P9 の決定。§5.6） |

未知のキーは誤り（打ち間違いを見逃さないため）。例外として、エディターの補完のための `$schema`（文字列）は受け付けて無視する。

実装で決めた規則（上の表に加えたもの。`src/console/config.ts`）:

- `access` は `groupObjectIds`・`policyIds`・`aud` の**どれか 1 つだけ**。`groupObjectIds` と `policyIds` は UUID の形。AUD は英数字 16〜128 文字
- `portal.*Origin` は `https://<host>` の形そのもの（末尾の `/`・パス・ポート以外の付加物・利用者情報を受け付けない。§9.3 で `Origin` と完全一致させるため）。`workers.dev` とそのサブドメインは大文字小文字を問わず拒否する
- `portal.regions` は `allowed`（1 件以上）と `default`（`allowed` に含まれること）がどちらも必須
- `boundaries[].issuers` の URL は `https`、クエリ・フラグメント・末尾の `/` なし。issuer の URL は境界・階層をまたいで重複してはいけない（鍵を境界 × 階層で分けるため。cto の D3）。issuer の `workers.dev` は拒否しない（issuer のホストは N9・G-8 で決める）
- 管理外の境界（`partner:*`）の Organization は `placement: "accounts"` だけ（先方の `ListAccounts` は読めない。§5.1）
- `roles[].permissions.managedPolicyArns` は AWS 管理ポリシー（`arn:aws:iam::aws:policy/...`）だけ。`inlinePolicyFiles` は下流のリポジトリ内の相対パス（絶対パスと `..` を受け付けない）
- ロールの `roleName`（IAM のロール名）も重複してはいけない。ロールの `name` から StackSets のパラメーター名（`read-only` → `ReadOnlyTeams`）を作るので、それが衝突する名前の組（例 `a-1` と `a1`）も誤り
- OU ID は Organization・種類をまたいで重複してはいけない（2 つの種類に同じ OU を割り当てない）。`kinds[].assign` のチームの一覧の中の重複も誤り
- `organizations[].accounts[].email` は 6〜64 文字の email の形

```json
      "inventoryRoleArn": "arn:aws:iam::<management-account-id>:role/awsbridge-inventory",
      "kindOus": { "A": ["<ou-id>"], "B": ["<ou-id>"], "C": ["<ou-id>"] }
    },
    {
      "name": "partner-x", "displayName": "<先方の名前>", "boundary": "partner:partner-x", "placement": "accounts",
      "accounts": [{ "accountId": "<account-id>", "name": "partner-x-dev", "kind": "P" }]
    }
  ],
  "inventory": { "accountEmail": { "managed": "full", "partner": "full" } }
}
```

- この例では、インフラ（`infra`）を全種類の ReadOnly に入れている（旧 Q-P1 を「許す」とした場合）。許さないなら `readonly` から `infra` を外す。その場合、Standard のポータルでインフラの一覧は空になる（生成の警告。§11.6）
- 管理外の先方の境界には Admin の issuer がないので、先方の種類 P に Admin のロールは割り当てられない（割り当てると生成のエラー）
- AUD は書いていない。Terraform の出力から入る（§11.4）

### 11.4 1 つの設定から生成するもの

| 生成するもの | 使う項目 | 方法 | 置き場所 |
|---|---|---|---|
| Access アプリとポリシー | `portal`（ホスト・`routing`）、`teams[].name` / `tier` / `access` | 下流の Terraform が設定ファイルを読み（`jsondecode(file(...))`）、入口・チームごと・Bypass のアプリを `for_each` で作る（Bypass は issuer をポータルのホストに置く場合だけ。console-login.md §3.1）。チームのアプリのポリシーは `access.groupObjectIds` だけを要求する（§9.1） | Cloudflare（Terraform の state は下流） |
| AUD → チームの対応 | Terraform の出力（チーム名 → AUD。`AWSBRIDGE_CONSOLE_AUD_FILE`） | 生成のタスクが Terraform の出力を読み、Worker 用の生成物に入れる。手書きの `access.aud` は Terraform を使わない構成のためのもの | Worker 用の生成物 |
| Worker 用の生成物（階層ごと） | その階層の `teams`（名前・表示名・AUD）・入口の AUD・`roles`（`name`・`roleName`・`displayName`・`sessionSeconds`）・`boundaries` の issuer・`portal` の値（もう一方の階層のオリジンは静的なリンク用に `peerOrigin` として入れる）・タグのキー・一覧の行 | `mise run console:config:generate` → `worker.standard.json`（常に作る）・`worker.admin.json`（Admin の階層のチームがあるときだけ。なくなれば前回の分を消す） | gitignore の生成物 → wrangler の `alias` |
| 表示用インベントリ（一覧の行） | `organizations`・`kinds`・`roles`・`inventory.accountEmail` と、`ListAccounts` の結果 | 種類の割り当てを展開して「アカウント × ロール → チーム」を作り、階層で分ける（§5.2） | Worker 用の生成物の一部 |
| StackSets のテンプレート | `roles`（`roleName`・`tier`・`sessionSeconds`・`permissions`） | **未実装**（K1 / K2 は G-9 で決める。いまはパラメーターの形 `stacksets.json` だけを生成する）。K1 なら、ロールの一覧からテンプレートを生成する。各ロールに、信頼ポリシー（その階層の issuer の OIDC プロバイダー、`aws:RequestTag/awsbridge_team` ∈ パラメーター、`TagKeys`、SourceIdentity 必須）と、`localhost` だけの `aws login` のポリシーを付ける。パラメーターが空のロールは作らない（`Conditions`） | 下流（生成して cfn-lint にかける） |
| StackSets のパラメーター | `kinds[].assign`、`organizations[].kindOus`（管理外・単独のアカウントは `accounts`） | 種類 × Organization ごとに「ロール → 受け付けるチーム（カンマ区切り）」。パラメーター名はロールの `name` から作る（`readonly` → `ReadonlyTeams`）。割り当てのないロールは空文字（テンプレートの `Conditions` で作らない）。ロールの定義（`roleName`・`tier`・`rolePath`・`sessionSeconds`・権限）と、タグのキー（`tagKey`）・audience（`audience`）・ロールのパスの接頭辞（`rolePathPrefix`）も同じファイルに入れる | `mise run console:config:generate` → `stacksets.json`。下流の CI が StackSets に反映する |
| 基盤の StackSet のパラメーター | `boundaries[].issuers` | Organization ごとに OIDC プロバイダー（Standard・Admin） | 同上（`stacksets.json` の `providers`） |
| Access の検査用 | `portal`、`teams[].tier` / `access`、AUD | チームごとの階層・ポリシーの元（`groupObjectIds` / `policyIds` / 手書きの AUD）・解決した AUD と、ポータルのオリジン・入口の AUD | `mise run console:config:generate` → `access.json`。CI で Terraform の出力・plan と突き合わせる（§11.5） |
| 管理外の先方に渡すもの | 先方の種類・境界 | 同じテンプレートと、先方用のパラメーター | 手順書と一緒に先方へ |
| wrangler の Custom Domain | `portal.*Origin`（R-H ならチーム名も） | 下流の `wrangler.<name>-console.jsonc` は手で書く。CI で設定ファイルと突き合わせる | 下流 |

**ロールを設定で増減できるようにしたことの影響**: 設計上申の種類の StackSet は、パラメーター `AdminTeams` / `DeveloperTeams` / `ReadOnlyTeams` の 3 つ固定の汎用テンプレートを上流に置く案だった。ロールを設定で定義すると、次の 2 案になる（§12.2 の G-9）。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **K1 テンプレートを生成する**（作成者の案） | 上流は生成器を持ち、下流が自分の `roles` からテンプレートを生成する | ロールの数と中身を下流が自由に決められる。個人用は 1 つでよい | テンプレートの実物が下流ごとに違う。上流のテストは生成器のテストになる。生成物を cfn-lint とレビューで確かめる |
| K2 枠を固定する | 上流のテンプレートに Admin / Developer / ReadOnly の 3 枠を置き、設定は名前・権限ポリシー・長さだけを変える | テンプレートを上流 1 か所でレビューできる | 4 つ目のロールが作れない。設定の自由度と見かけが食い違う |

**Admin のチームを明示する**: 設計上申 §4.6.5 は「種類の定義はチーム名で書き、テンプレートが Admin のときだけ `-elevated` を付ける」案だった。この設定では、Admin の階層のチーム（例 `infra-elevated`）を `teams` に明示し、`kinds` でも明示して割り当てる。名前を暗黙に変える規則がなくなり、Access アプリ・Entra のグループ・タグの値・信頼ポリシーが同じ名前で揃う。階層の一致（§11.3）を検査するので、Standard のチームを Admin のロールに割り当てる誤りは生成で止まる（§12.2 の G-9）。

### 11.5 検証（CI）と cto の条件との整合

下流の CI（PR ごと・適用のあと・定期）で次を確かめる。設定ファイルが唯一の元なので、検査の目的は「生成し忘れ・適用し忘れ・手で変えた」を見つけること。

チームを足す PR の時点では Access アプリがまだなく、AUD もない。そのため、反映は次の順にし、AUD を要る検査は適用のあとに回す。

1. PR: スキーマと参照の検査（AUD なしの生成。`mise run console:config:check`。`terraform plan` は差分の確認とレビューのために出すだけ）
2. マージ → `terraform apply`（Access アプリができ、AUD が出力に出る）
3. AUD を要る生成（Worker 用の生成物。`AWSBRIDGE_CONSOLE_AUD_FILE` に Terraform の出力を渡して `mise run console:config:generate`）→ Worker のデプロイ
4. 適用のあとと定期: `terraform plan` に差分がないこと、AUD の対応の一致（`AWSBRIDGE_CONSOLE_AUD_FILE` を渡した `mise run console:config:check` は、AUD の欠落・食い違い・重複・設定にないチームまで検査する）

| 検査 | 内容 | 時機 |
|---|---|---|
| スキーマと参照 | §11.3 の規則と §11.6 のエラー（AUD の有無を除く） | PR |
| Access | `terraform plan` に差分がない。Terraform の出力のチーム → AUD が、Worker 用の生成物の対応と一致する（全単射）。チームのアプリのポリシーが、そのチームの `groupObjectIds` だけを要求している | 適用のあと・定期（ポリシーの形は PR の plan でも見る） |
| StackSets | 生成したテンプレートとパラメーターが、実際の StackSets と一致する（読み取りだけ）。ドリフト検出 | 定期 |
| OU | `kindOus` の OU が入れ子になっていない。どの種類の OU にも属さない管理下のアカウントの件数（警告） | 定期（Organizations の読み取り） |
| 分離 | Worker 用の生成物の分離（§9.10） | PR |
| wrangler | Custom Domain のホストが `portal.*Origin` と一致する | PR |

cto の条件との整合:

| cto の条件 | この設計での答え |
|---|---|
| AUD → チームの対応は Access の Terraform と同じ元から生成する | 元は設定ファイルの `teams`。Terraform はそこから Access アプリを作り、Worker の対応は Terraform の出力から生成する。どちらかだけを変える経路がない。手書きの `access.aud` が Terraform の出力と食い違えば生成のエラー。会社の下流では手書きの AUD を使わない（CI で `access.aud` がないことを確かめる） |
| 種類の定義は private リポジトリで管理し、CODEOWNERS とレビューを通す | 設定ファイルは下流（private）にだけ置く。CODEOWNERS で設定ファイルのレビュー担当を**利用者本人**にする（Q-P10 の決定）。Admin の階層の割り当てを広げる差分（`kinds[].assign` の Admin のロールにチームが増える、Admin のロールの権限が増える）と、**どの階層でもロールの `permissions` か `tier` を変える差分**は、CI が差分から検出して目立つように示す（PR のラベルや警告）。承認はレビュー担当 1 人でよい（利用者の決定。2 人の承認は求めない）。ロールの `tier` は設定の自己申告で、強い権限を Standard のロールに付ければ Admin の分離（別デプロイ・KMS）を通らずに済んでしまうため。Standard のロールに付けてよい権限の上限（例 `AdministratorAccess` や IAM の書き込みを禁じる）を生成で検査するかは G-9 で決める（いまの実装は検査しない）。上流のスキーマや生成器の変更は、下流で upstream を取り込む PR として同じレビューを通る |
| Worker は対応表を権威として持たない。表示用の一覧は持ってよい | `kinds` は Worker に入れない。Worker に入るのは、展開済みの表示用の一覧の行と、AUD → チームの対応（許可の範囲を持たない識別用。§0）だけ |
| Access ポリシーの形を CI で検査する | §11.5 の Access の検査 |

### 11.6 設定の誤りの扱い

方針: **手元と CI で見つけられる誤りは、すべて生成（ビルド）の時点でエラーにし、デプロイさせない**。MCP 用の `profiles.json` は欠落をビルド時のエラーにし、中身の誤りは実行時の 500 `server_misconfigured` にしていた。コンソールログイン用は生成の段階があるので、中身の誤りも前に寄せる。Worker の実行時の検査は、生成物が壊れていないことの確認（多重の防御）に限る。

| 誤り | 見つける時点 | 扱い |
|---|---|---|
| 設定ファイルがない | 生成・ビルド | エラー（wrangler の alias の解決エラーも同じ） |
| 構文・型・必須の欠落・未知のキー・`schemaVersion` の不一致 | 生成 | エラー。キーのパスと誤りの種別（`required`・`unknown_key` など）を出し、値は出さない。利用者が書いたキーのうち名前の形でないもの（AUD・email・12 桁の数字を含むものなど）はパスの中でも `<redacted>` にする |
| 未知のチーム・ロール（`kinds[].assign` の参照先がない）、未知の種類・境界（`organizations` の参照先がない） | 生成 | エラー |
| 名前の重複（チーム・ロール・種類・Organization）、AUD の重複、アカウント ID の重複 | 生成 | エラー |
| 階層の不一致（Admin のロールに Standard のチーム、など）。境界にない階層の issuer が要る割り当て | 生成 | エラー |
| `adminOrigin` がないのに Admin の階層がある。`standardOrigin` と `adminOrigin` が同じ。`workers.dev` のホスト | 生成 | エラー |
| チームの AUD がない（Terraform の出力にも手書きにもない） | デプロイ用の生成 | エラー（profiles.json の欠落と同じく、黙って動かさない）。生成は全階層をまとめて行うので、どの階層のチームの AUD が欠けても全体がエラーになる（Admin の階層をまだ作らないなら、設定に Admin のチームを書かない）。入口の AUD も、その階層のチームが 2 つ以上なら要る。PR の検査（AUD なしの生成）では誤りにしない（§11.5 の順） |
| 手書きの AUD と Terraform の出力が違う | 生成 | エラー |
| どの種類にも割り当てられていないチーム・ロール | 生成 | 警告（一覧が空になるだけで、権限は広がらない。旧 Q-P1 の選び方で起きうる） |
| どの種類の OU にも属さない管理下のアカウント | インベントリの生成 | 警告（一覧に出さず、件数を出す） |
| OU の入れ子 | CI（定期） | エラー（同名のロールが 2 つの StackSet から配られて衝突する。設計上申 §4.6.6） |
| 生成物の不整合（他の階層の行・チームの混入、壊れた JSON） | Worker の初回の要求 | 500 `server_misconfigured`。ログは `config: invalid console config: <種別>` だけで、値は出さない（profiles と同じ） |
| 要求の AUD が生成物にない | 要求のたび | 設定の誤りではない。403 `unknown_audience`（§9.4） |

### 11.7 個人利用の最小構成

チーム 1 つ、ロール 1〜2 つ、Organization なし（単独のアカウント）でも重くならないようにする。

```json
{
  "schemaVersion": 1,
  "portal": { "standardOrigin": "https://aws.<domain>" },
  "teams": [
    { "name": "me", "displayName": "自分", "access": { "aud": "<access-aud>" } }
  ],
  "roles": [
    { "name": "readonly", "roleName": "FederatedViewer", "sessionSeconds": 43200,
      "permissions": { "managedPolicyArns": ["arn:aws:iam::aws:policy/ReadOnlyAccess"] } },
    { "name": "developer", "roleName": "FederatedDeveloper", "sessionSeconds": 14400,
      "permissions": { "managedPolicyArns": ["arn:aws:iam::aws:policy/PowerUserAccess"] } }
  ],
  "kinds": [{ "name": "default", "assign": { "readonly": ["me"], "developer": ["me"] } }],
  "boundaries": [{ "name": "managed", "issuers": { "standard": "https://<issuer-host>/<standard-path>" } }],
  "organizations": [
    { "name": "personal", "boundary": "managed", "placement": "accounts",
      "accounts": [{ "accountId": "<account-id>", "name": "my-sandbox", "kind": "default" }] }
  ]
}
```

| 省けるもの | 理由・代わり |
|---|---|
| Admin の階層（`adminOrigin`・Admin のチーム・KMS） | Admin の階層がなければ Admin のデプロイを作らない。強い権限を Standard の階層のロールとして持つかは下流の判断とする案（会社用の分離の条件を個人用には課さない）[推測: §12.2 の G-9 で確かめる] |
| Terraform | Access アプリを 1 つ手で作り（ポリシーは自分の email など）、AUD を `access.aud` に書く。AUD を書き忘れれば生成のエラー。cto の「同じ元から生成」の条件は会社用の条件と読み、個人用には課さない [推測: §12.2 の G-9 で確かめる] |
| 入口のアプリ | チームが 1 つなら、そのチームのアプリでホスト全体を守り、S0 はそのチームの S1 へ移すだけにする [推測: 実装の案。N1 と一緒に確かめる] |
| StackSets・インベントリのジョブ | 単独のアカウントは、生成したテンプレートを CloudFormation で流す（MCP 用の `mise run deploy:aws` と同じ形）。一覧は `accounts` から作る |
| 省略できる項目の既定値 | `tier` は `standard`、`displayName` は `name`、`routing` は `path`、`regions` なし、`inventory.accountEmail` は管理下・管理外とも `full` |
| CI の検査 | スキーマと参照の検査（`mise run console:config:check`）だけで足りる。生成は `mise run console:config:generate`（手書きの AUD を使うので、Terraform の出力は要らない） |

### 11.8 下流の設定で決めること

上流（この文書）では決めず、各下流が設定ファイルで決める事項。会社の下流で決めるときの作成者の案も書く。

| 事項 | 設定の項目 | 会社用の作成者の案 |
|---|---|---|
| 上位の権限を持つチーム（例 インフラ）が、同じアカウントの ReadOnly も使えるか（旧 Q-P1） | `kinds[].assign` の `readonly` にそのチームを入れるか | 入れる。入れないと Standard のポータルでインフラの一覧が空になり、普段の作業も Admin で入ることになる |
| ロールごとのセッションの長さ（旧 Q-P2） | `roles[].sessionSeconds` | 例 ReadOnly 12 時間、Developer 4〜8 時間、Admin 1〜2 時間 |
| 問い合わせ先（旧 Q-P6） | `portal.supportUrl` | 社内の窓口 |
| チームとロールの一覧、Developer の権限の中身 | `teams`・`roles[].permissions` | 設計上申 §4.6 の 3 チーム・3 ロール |
| ポータルのホスト名 | `portal.standardOrigin` / `adminOrigin` | `<domain>` の下で、段階 1 の前に確定する（§3.1） |
| 一覧に出すアカウントの email | `inventory.accountEmail` | **決定**（Q-P9）: 既定のまま、管理下・管理外とも `full`（すべて表示） |

### 12.4 却下した案

| 案 | 却下の理由 |
|---|---|
| 一覧から 1 クリックでログイン（POST）する | 誤操作と、1 回の操作で発行される面が広がる。S2 で 1 回押す形でも操作は 2 回で済む |
| ロール ARN を自由に入力してログインする | 利用者の入力をそのまま STS に渡す面が増える。一覧にないロールは一覧の再生成で解決する |
| ログイン URL を表示・コピーする | URL はセッションそのもの。AWS も 302 で渡すことを勧めている |
| ポータルが CLI の認証情報を発行する（表示・`credential_process`） | 認証情報を Worker の外に出さない。`aws login` で足りる（利用者の回答） |
| Standard の一覧に Admin の行（または件数）を出す | Admin のデータが Standard のデプロイに入り、分離が崩れる |
| チーム・ロール・種類を上流のコードや文書に固定する | awsbridge は public の OSS で、組織ごとに値が違う。上流はスキーマと例だけを持つ（§11.1） |
| 設定ファイルをそのまま Worker にバンドルする（profiles.json と同じ形） | Standard のバンドルに Admin の AUD と種類の表が入り、§9.10 の分離と「Worker は対応表を権威として持たない」に反する。生成物を挟む（§11.2） |
| 設定を Worker の環境変数（vars / secret）に置く | 1 つ 5 KB の上限に収まらない（MCP 用の `AWS_PROFILES` を廃止したのと同じ理由。architecture.md） |
| AUD を設定ファイルに手で書いて Terraform と別に管理する（会社用） | cto の条件（同じ元から生成）に反し、食い違いうる。Terraform の出力から生成する（§11.4） |
| アカウントの email を検索するための JSON の API を足す | 外から叩ける面が増える。埋め込みの JSON で足りる（§5.6） |
| チームを URL のパス・ホスト・利用者の入力から決める | cto の条件（AUD だけから決める）に反する。パスは経路の振り分けにだけ使う |
| CSRF を Access の Cookie の SameSite だけに頼る | Access の設定に依存する（既定は None） |
| コンソールのセッションの有無を検出して案内を出し分ける | 別のオリジンの状態はポータルから見えない |
| 非公式に知られたサインアウトの URL を組み込む | 公式文書で確かめられない。P-1 で公式の手順を確かめてから検討する |
